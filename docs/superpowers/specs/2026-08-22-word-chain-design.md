## 1. 배경

헤더에 `게임 → 끝말잇기` 메뉴가 있고 `/games/word-chain` 이 "준비 중입니다" 화면으로 자리만 잡고 있다. 이제 그 자리를 채운다.

**이 프로젝트에서 처음으로 실시간 통신이 들어온다.** 지금까지는 전부 요청-응답이었고, 상태의 진실은 서버 DB 에 있고 화면은 물어보면 되는 구조였다. 끝말잇기는 그렇지 않다 — 남의 입력, 턴 이동, 타이머가 내가 아무것도 하지 않아도 화면에 도착해야 한다.

동시에 **외부 API 의존**도 처음이다. 국립국어원 표준국어대사전에 일일 5만 회 제한이 있어 캐시가 선택이 아니라 필수다.

## 2. 범위

이 문서는 **전체 그림 + A 를 상세히** 다룬다. B·C·D 는 방향만 정하고, 구현 직전에 각각 스펙을 따로 쓴다.

| | 덩어리 | 이 문서에서 |
|---|---|---|
| **A** | 방 목록 · 생성 · 입장 | 상세 (7장) |
| **B** | 대기실 — 아바타, 준비, 방장 양도 | 방향만 |
| **C** | 게임 — 턴, 타이머, 무대 연출 | 방향만 |
| **D** | 사전 판정 + 캐시 | 방향만 (6장) |

한 번에 만들 크기가 아니라서 나눴다. **A→B→C+D 순서**다. D 는 C 없이는 쓸 데가 없어 함께 간다.

## 4. 상태 기계

**방**

```
WAITING ──전원 준비──> PLAYING ──1인 남음──> WAITING
```

**참가자**

```
대기실   WAITING ⇄ READY
게임 중  ALIVE → ELIMINATED
         SPECTATOR (게임 중에 들어온 사람)
```

관전자는 다음 판이 시작될 때 `WAITING` 으로 합류한다.

### 4.1 서버가 갖는 게임 상태

```
currentWord   마지막으로 통과한 단어
turnUserId    지금 차례
turnEndsAt    턴이 끝나는 절대 시각
usedWords     이미 나온 단어 (재사용 금지가 켜졌을 때)
turnOrder     살아있는 사람 순서
```

**`turnEndsAt` 은 절대 시각으로 내려준다.** 남은 초를 내려주면 네트워크 지연만큼 어긋난다. 화면은 이 값으로 카운트다운을 **그리기만** 하고, 초과 판정은 서버 스케줄러가 한다.

### 4.2 방 운영 규칙

| 상황 | 처리 |
|---|---|
| 방장이 나감 | 남은 사람 중 **가장 먼저 들어온 사람에게 자동 양도** |
| 마지막 사람이 나감 | 방 삭제 |
| 게임 중 누가 나감 | 그 사람만 탈락. 자기 차례였으면 다음 사람으로 |
| 게임 중 입장 | **관전**으로 입장, 다음 판부터 참가 |
| 소켓 끊김 | 퇴장으로 본다 |

**소켓이 끊긴 것을 퇴장으로 보지 않으면 유령 인원이 정원을 먹는다.** 브라우저를 닫아도 방에 남아 있으면 10명짜리 방이 금세 못 쓰게 된다.

## 5. 실시간 — STOMP

```
구독  /topic/rooms              방 목록의 인원 변화
      /topic/rooms/{id}         방 상태 전체
      /user/queue/errors        나에게만 가는 오류

전송  /app/rooms/{id}/ready     준비 토글
      /app/rooms/{id}/transfer  방장 양도
      /app/rooms/{id}/start     게임 시작 (방장만)
      /app/rooms/{id}/answer    답 제출
```

**방 상태는 통째로 브로드캐스트한다.** 참가자 목록·턴·말풍선을 각각 다른 메시지로 쪼개면 순서가 뒤집혔을 때 화면이 어긋나고, 재접속한 사람에게 현재 상태를 다시 만들어 줄 방법이 없어진다. 10명짜리 방의 상태는 작다.

**오답도 모두에게 브로드캐스트한다.** 말풍선에 답이 뜨는 것이 이 게임의 재미라 틀린 답도 보여야 한다. `/user/queue/errors` 는 "방장이 아닌데 시작을 눌렀다" 같은 **본인만 알면 되는 것**에 쓴다.

### 5.1 인증

access token 을 CONNECT 프레임 헤더에 실어 보내고 서버가 검증해 `Principal` 을 세운다.

**연결 전에 `reissueOnce()` 를 한 번 거친다.** 토큰이 만료된 채로 연결하면 실패하는데, 소켓은 REST 처럼 401 을 받고 재발급하는 흐름이 없다.

한 번 맺은 연결은 토큰이 만료돼도 유지된다. 인증은 연결 시점에만 한다.

### 5.2 배포 — 소켓은 Netlify 를 거치지 않는다

`netlify.toml` 의 200 rewrite 는 `/api/*` 를 Railway 로 넘기지만 **WebSocket 업그레이드는 넘기지 못한다**(구현 전 반드시 실측할 것). 넘기지 못한다면 소켓만 Railway 주소에 직접 붙는다.

REST 는 지금처럼 프록시를 거친다. **refresh 쿠키가 서드파티 쿠키가 되면 안 되기 때문**이고, 소켓은 쿠키를 쓰지 않으므로 직접 붙어도 그 문제가 없다.

## 6. 사전 판정과 캐시 (D 방향)

**2026-08-23 갱신.** 아래는 백엔드가 실제 키로 호출해 확인한 결과에 맞춰 고쳤다. 처음 쓴
내용에 틀린 것이 있었다.

```
답 제출 → Caffeine 캐시 조회 ─hit  → 판정
                            └miss → 표준국어대사전 API → 캐시 저장 → 판정
```

### 6.1 JSON 으로 요청한다 (2026-08-23 정정)

처음에 "XML 을 써야 한다"고 적었다. **틀렸다.** 근거로 삼은 표에 조건이 하나 빠져 있었다.

구분이 필요한 이유 자체는 맞다 — "없는 단어"와 "키가 죽었다"를 섞으면 안 된다. 그런데
**`advanced=y` 만 붙으면 JSON 도 갈린다.**

| 상황 | `advanced=y` 없이 | **`advanced=y` 와 함께** |
|---|---|---|
| 결과 0건 | 빈 본문 | **`{}`** |
| 키·파라미터 오류 | 빈 본문 | 빈 본문 |

그리고 `advanced=y` 는 **어차피 보내야 한다.** 없으면 `pos=1`(명사)과 `type1=word` 가 조용히
무시된다(6.3). 전제 조건이 공짜다.

**XML 이 더 주는 것은 오류 코드 하나뿐이다** — `020`(등록 안 된 키) · `021`(사용 중지) ·
`103`(파라미터 오류). 게임 로직에는 차이가 없다. 셋 다 판정 불가다. 값이 생기는 자리는 운영
로그뿐인데, 그 대가가 XML 파서 의존성과 JSON 일색인 코드의 두 번째 직렬화 형식이다.

**본문이 파싱되면 질의가 성립한 것이고, 비어 있으면 오류다.** `res.json()` 은 빈 본문에서
`SyntaxError` 를 던지므로 그것으로 갈린다.

### 6.2 오류는 캐시하지 않는다

처음에 "실패도 캐시한다"고 적었는데 **위험하다.** 빈 응답을 "없는 단어"로 저장하면, 키가
만료되거나 한도가 터진 동안 제출된 **모든 단어가 오답으로 굳는다.** TTL 이 1일이라 하루
종일 게임이 망가진다.

- **캐시하는 것**: 본문이 파싱된 결과로 확정한 있음·없음
- **캐시하지 않는 것**: 빈 본문, 파싱 실패, 네트워크 실패

없는 단어를 캐시하는 것 자체는 맞다 — 같은 오타가 반복되므로 호출이 크게 준다. 문제는
**오류를 없음으로 착각하는 것**이다.

**이 방식은 틀려도 안전한 쪽으로 틀린다.** 나중에 저쪽이 바뀌어 "없음"까지 빈 본문이 되면
우리는 그것을 오류로 보고 캐시하지 않는다. 판정을 못 할 뿐 틀린 답을 굳히지는 않는다.
반대가 훨씬 나쁘다.

### 6.3 요청 파라미터

```
GET https://stdict.korean.go.kr/api/search.do
    ?key={KEY}&req_type=json&q={단어}
    &advanced=y&method=exact&pos=1&type1=word
```

| | 왜 필요한가 |
|---|---|
| `advanced=y` | **없으면 `pos`·`type1` 이 무시되고, 0건과 오류도 안 갈린다**(6.1) |
| `method=exact` | 기본값이지만 명시한다 |
| `pos=1` | 명사만 |
| `type1=word` | 없으면 속담·관용구가 표제어로 섞여 나온다 |

`total >= 1` 이면 통과다. 동음이의어는 별개 항목으로 오지만 판정에는 쓰지 않는다.

**`num` 을 건드리지 말 것.** 10 미만이면 오류인데 그것도 빈 본문이라 "없는 단어"처럼 보인다.

### 6.4 표제어 정규화 — 방향이 반대다

표제어에는 붙임표가 흔하다 (`가가-례`). 3음절 명사 300개 표본에 288회 나왔다.

**그런데 검색은 붙임표 없는 형태로 해야 맞는다** — `q=가가례` 는 1건, `q=가가-례` 는 0건이다.
즉 **사용자가 친 것을 그대로 보내면 된다.** 정규화가 필요한 쪽은 응답이다. 표제어를 화면에
보여주거나 입력과 비교할 때만 `-` 를 지운다.

### 6.5 첫 단어는 씨앗 목록에서 뽑는다

**API 랜덤 추출은 기술적으로 되지만 쓸 수 없다.** 음절 수 필터와 페이지 이동을 조합하면
뽑히기는 하는데, 실제로 나오는 것이 `사래전`·`마간석`·`하악골`·`나란타` 같은 지명·전문어·
음역어다. 표준국어대사전이 그것들을 다 담고 있어 가나다순에서 무작위로 집으면 그 비율이
그대로 나온다.

**서버가 씨앗 목록을 상수로 들고 거기서 뽑는다.** 백엔드가 50개를 만들어 뒀고, 두 가지를
실측으로 걸렀다.

1. 표준국어대사전에 **명사로 존재**하는가
2. **끝 글자로 이어갈 3음절 명사가 100개 이상**인가

두 번째가 결정적이었다. `초콜릿`은 `릿`으로 시작하는 3음절 명사가 **0개**라 첫 턴에 게임이
끝난다. `젓가락`·`도시락`도 4개뿐이다.

목록을 늘릴 때도 이 두 검사를 그대로 돌린다. 테이블도 API 도 필요 없다.

### 6.6 아직 모르는 것

- **일일 한도를 넘겼을 때의 응답.** 확인하려면 5만 건을 태워야 해서 실측하지 않았다.
  가장 가까운 코드는 `021`(일시적으로 사용 중지된 인증 키)이다
- **초당 호출 제한**이 있는지

### 6.7 정해야 할 것

**사전을 못 쓰는 상태에서 게임을 어떻게 할 것인가.** 통과시킬지(느슨), 막을지(엄격),
그 판을 중단할지. 구현 요청서에서 정한다.

**키는 하나뿐이다.** 사용자당 한 개라 개발용·운영용을 나눌 수 없고, 로컬 테스트가 운영
할당량을 쓴다. 로컬은 스텁으로 돌리거나 TTL 을 길게 두는 쪽을 같이 정한다.

### 6.8 판정 순서

싼 것부터 한다.

```
1. 3글자인가          (문자열)
2. 앞 단어와 이어지나  (두음법칙 변환표)
3. 이미 나왔나        (usedWords)
4. 사전에 있는 명사인가 (캐시 → 외부 API)
```

**외부 호출은 맨 마지막이다.** 앞의 셋에서 걸리는 답이 대부분이다.

## 7. A 상세 — 방 목록 · 생성 · 입장

### 7.1 화면

```
/games/word-chain

  끝말잇기                                      [방 만들기]

  ┌──────────────────────────────────────────┐
  │ 🔒 점심내기 한판                  대기중  3/10 │
  │    개발팀 모여라                  게임중  7/10 │
  └──────────────────────────────────────────┘
```

- 비밀번호가 걸린 방은 자물쇠
- `대기중` / `게임중`
- `3/10` — 현재 인원 / 정원

### 7.2 API

| 메서드 | 경로 | 요청 | 성공 |
|---|---|---|---|
| GET | `/api/rooms` | | 200 `RoomSummary[]` |
| POST | `/api/rooms` | `{name, password?}` | 201 `RoomSummary` |
| POST | `/api/rooms/{id}/join` | `{password?}` | 200 `RoomSummary` |

```json
// RoomSummary
{ "id": 7, "name": "점심내기 한판", "hostName": "김성호",
  "playerCount": 3, "capacity": 10, "locked": true, "status": "WAITING" }
```

**세 응답이 같은 모양이다.** 만들거나 들어간 직후에도 목록과 같은 정보를 쓰므로 형태를 나눌 이유가 없다. 참가자 목록·턴 같은 방 안의 상태는 REST 로 주지 않는다 — 구독하면 곧바로 브로드캐스트로 온다.

**입장은 REST 로 검증하고, 통과한 뒤에 화면을 옮기고 STOMP 를 구독한다.** 소켓에서 비밀번호를 검사하면 실패했을 때 이미 맺은 연결을 되돌려야 해서 번거롭다.

| 상황 | HTTP | `code` |
|---|---|---|
| 이름이 비었거나 30자 이상 | 400 | `INVALID_INPUT` |
| 정원 초과 | 409 | `ROOM_FULL` |
| 비밀번호 틀림 | 403 | `WRONG_ROOM_PASSWORD` |
| 없는 방 | 404 | `ROOM_NOT_FOUND` |

게임 중인 방에 들어가면 200 이고 관전자로 붙는다.

### 7.3 목록 갱신

첫 로드는 REST, 이후는 `/topic/rooms` 구독으로 인원 변화를 받는다. **목록 화면에서 폴링하지 않는다** — 어차피 소켓을 쓰는 김에 같은 통로를 쓴다.

### 7.4 프론트 배치

```
src/features/word-chain/
├── api/          REST (방 목록·생성·입장)
├── model/        상태 타입, 규칙
└── ui/           RoomList · RoomCard · CreateRoomDialog

src/shared/ws/    STOMP 클라이언트. 도메인을 모른다

src/pages/
├── WordChainRoomsPage   /games/word-chain
└── WordChainRoomPage    /games/word-chain/:roomId
```

`shared/ws` 가 `shared` 인 이유는 도메인 지식이 없기 때문이다 — "연결하고, 구독하고, 보낸다"가 전부다. 방·게임을 알면 `features` 로 내려가야 한다.

## 8. 아바타

기본 2종(남/여) 중 선택한다. 3D 클레이 스타일의 정사각 이미지이고 `public/avatars/` 에 둔다.

**지금은 커스터마이즈를 만들지 않는다.** 색·머리 모양을 고르게 하려면 조합을 저장할 곳과 렌더링 방식을 정해야 하는데, 그 전에 게임이 재미있는지가 먼저다.

## 9. 폐기한 대안

**SSE + REST.** 서버→클라이언트만 필요하다면 맞지만, 답 제출·준비·양도가 전부 서버로 가는 양방향이라 연결이 둘로 나뉜다. 한 통로로 끝나는 STOMP 가 낫다.

**폴링.** 타이머가 초 단위라 1초 간격이 필요하고, 10명이면 방 하나에 초당 10회다. 스포트라이트와 말풍선 연출도 뚝뚝 끊긴다.

**Redis 로 방 상태 관리.** 서버가 한 대라 근거가 없다. 여러 대가 되는 날 `SimpleBroker` 와 함께 다시 본다.

**방을 DB 에 영속.** 방은 마지막 사람이 나가면 사라지는 휘발성 자원이다. 게임 기록을 남기게 되면 그때 테이블을 만든다.

**한방단어 사전 검사.** "이 글자로 시작하는 3글자 명사가 있는가"를 매번 물으면 호출이 배로 든다. 3글자 고정이라 흔하지도 않다.
