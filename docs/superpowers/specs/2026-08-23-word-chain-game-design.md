# 끝말잇기 C — 게임 진행 설계

작성일: 2026-08-23
대상: `front/company-app` + `backend/company-backend`
선행 문서: [전체 그림](2026-08-22-word-chain-design.md) · [대기실](2026-08-23-word-chain-room-design.md)

## 1. 범위

전체 그림의 **C** 다. 방장이 시작을 누른 뒤부터 최후 1인이 남을 때까지.

| 들어감 | 안 들어감 |
|---|---|
| 턴 · 타이머 · 순서 | 사전 실연동 — D |
| 답 제출과 판정 | 전적 · 통계 |
| 말풍선 · 스포트라이트 | 채팅 |
| 탈락과 승리 | 방 목록 실시간 갱신 |
| 관전 | 재접속 복구 |

사전은 **인터페이스만** 정한다. 실제 표준국어대사전 연동과 캐시는 D 다. C 에서는 스텁으로
돌린다 — 판정 규칙과 화면이 사전보다 먼저 서야 한다.

## 2. 결정 요약

전체 그림 3장의 결정표를 그대로 따르고, C 에서 새로 정한 것만 적는다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 턴 시간 | 방장이 **3 · 5 · 7초** 중 선택, **기본 3초** | |
| 재시도 | **턴당 3번** | 오답의 대가가 시간뿐이면 마구 던지는 게 최적이 된다. 사전 호출이 무제한으로 열린다 |
| 3번 소진 | **즉시 탈락** (시간이 남아도) | 남은 시간을 흘려보내면 아홉 명이 아무 일도 안 일어나는 화면을 본다 |
| 판정 대기 중 | 말풍선을 **`PENDING`** 으로 먼저 띄운다 | 접수됐는지 모르면 또 낸다 — 기회가 3번뿐이라 하나를 날린다 |
| 제출 시각 | **받은 순간**에 찍는다 | 판정 후에 찍으면 제때 낸 사람이 서버 사정으로 탈락한다 |
| 시계 | 브로드캐스트에 **`serverNow`** 를 싣는다 | 3초 턴에서 0.5초 시계 오차는 17%다 |
| 옵션 변경 | **대기실에서 방장이** | 방 만들 때 정하면 사람이 모인 뒤에 못 바꾼다 |
| 옵션의 자리 | **방 레벨** (`game` 이 아니라) | 한 판도 안 한 방은 `game` 이 `null` 이라 실을 자리가 없다. 4.0 참고 |
| 게임 상태 | 기존 `RoomState` 에 **`game` 하나** | 전용 토픽을 파면 참가자 목록과 턴이 따로 와 순서가 뒤집힌다 |
| 좌석 | **판이 끝날 때까지 안 움직인다** | 차례마다 아바타가 이동하면 3초 간격으로 화면이 출렁인다 |

### 3초 기본이 만든 것

기본을 3초로 정한 것은 사용자의 결정이다. 가혹하다는 점은 짚었고 그대로 간다. 다만 **세 가지가
따라온다** — 6장에 모아뒀다.

1. 클라이언트 시계 오차가 드러난다
2. 한글 조합 중 Enter 가 기회를 통째로 먹는다
3. 사전 타임아웃이 1초 아래여야 하고, 그만큼 **미확인 통과가 늘어난다**

**턴당 3번은 3초에서도 도달 가능한 규칙이다.** 판정이 매번 사전 왕복을 내지 않기 때문이다.

| 오답의 종류 | 왕복 |
|---|---|
| 세 글자 아님 · 안 이어짐 · 이미 나옴 | 소켓 왕복만. **사전까지 가지 않는다** |
| 사전에 있는지 확인, 캐시 히트 | 인메모리라 사실상 즉시 |
| 사전에 있는지 확인, 캐시 미스 | 느리다. 6.3 의 타임아웃이 상한을 건다 |

**급할 때 나오는 오답은 대부분 첫 줄이다** — 앞 글자를 잘못 봤거나 이미 나온 단어를 낸다.
치는 데 0.8초, 판정에 0.15초면 3초에 두세 번이 나온다.

## 3. 한 턴의 흐름

```
턴 시작    turnEndsAt = now + turnSeconds
          triesLeft = 3
              ↓
제출       접수 시각을 그 자리에서 찍는다
              ↓  PENDING 브로드캐스트
판정       ① 3글자인가            (문자열)
          ② 앞 단어와 이어지나    (두음법칙 변환표)
          ③ 이미 나왔나          (noReuse 가 켜졌을 때)
          ④ 사전에 있는 명사인가  (캐시 → API, 짧은 타임아웃)
              ↓  결과 브로드캐스트
통과       currentWord 갱신 → 다음 살아있는 사람
오답       같은 사람 턴 유지, triesLeft -1
```

**외부 호출은 맨 마지막이다.** 앞의 셋에서 걸리는 답이 대부분이라 사전까지 가는 제출이 크게
준다. 전체 그림 6.10 과 같은 순서다.

### 3.1 탈락 조건은 둘이다

| | |
|---|---|
| 시간 초과 | `turnEndsAt` 을 넘겼는데 접수된 제출이 없다 |
| 기회 소진 | `triesLeft` 가 0이 됐다 |

**시간 초과 판정은 "제출이 하나도 없었는가"다.** 시간 안에 냈는데 판정이 늦게 끝나는 경우가
있으므로, 접수된 제출이 있으면 그 결과를 기다린다. 안 그러면 제때 낸 사람이 서버 사정으로
탈락한다.

**기다린 결과가 오답이고 이미 `turnEndsAt` 을 지났으면 시간 초과 탈락이다.** 기회가 남아
있어도 그렇다. 기다린 것은 그 제출이 통과할 기회를 주려던 것이지 시간을 늘려주려던 것이
아니다. 이걸 정하지 않으면 3초 턴에서 느린 판정이 곧 시간 연장이 되어, 사전이 느릴수록 유리해진다.

### 3.2 시간 초과는 서버가 스스로 깨어나 잡는다

제출이 없으면 아무 이벤트도 안 일어난다. 기본 턴이 3초라 좌석 회수용 주기 스케줄러(10초)로는
못 잡는다.

**턴마다 `turnEndsAt` 에 일회성 예약을 걸되 취소하지 않는다.** 깨어나면 그 방이 아직 같은
턴인지(`turnEndsAt` 이 그대로인지) 보고, 아니면 아무것도 하지 않는다.

취소 핸들 맵이 필요 없다 — 대기실 설계에서 세션 매핑을 별도 맵으로 두지 않은 것과 같은
이유다. 정밀도도 훑기 주기에 묶이지 않는다. 헛되이 깨어나는 예약이 턴마다 하나씩 생기지만
3초 턴이면 방당 초당 0.3개다.

### 3.3 판이 끝나는 조건

**살아있는 사람이 1명이 되면** 그 사람이 승리하고 방이 `WAITING` 으로 돌아간다.

**이때 모두의 `ready` 를 `false` 로 되돌린다.** 안 그러면 이전 판의 준비 상태가 그대로 남아,
결과를 보는 중에 방장이 누르면 아무도 동의하지 않은 채 다음 판이 시작된다. 마지막 사람이
준비를 누르는 순간 자동 시작되지 않게 한 것과 같은 이유다 — **손이 버튼 위에 있는 채로 판이
시작되면 안 된다.**

게임 중에 사람이 나가도 같다 — 나간 사람은 탈락 처리하고, 그 결과 1명이 남으면 거기서 끝난다.
자기 차례에 나갔으면 다음 사람으로 넘긴다.

## 4. 상태

```
room                          (기존 방 상태에 추가)
  serverNow     long          이 메시지를 보낸 서버 시각
  turnSeconds   int           3 · 5 · 7. 기본 3
  noReuse       boolean       재사용 금지. 기본 false

game                          진행 중이거나 방금 끝난 판. 없으면 null
  currentWord   String        마지막으로 통과한 단어
  turnUserId    Long | null   지금 차례. 판이 끝나면 null
  turnEndsAt    long | null   턴이 끝나는 절대 시각 (epoch ms). 판이 끝나면 null
  triesLeft     int           이번 턴에 남은 기회
  usedWords     String[]      이미 나온 단어
  turnOrder     Long[]        이 판에 참가하는 사람. 랜덤 순서
  eliminated    Long[]        그중 탈락한 사람
  bubbles       Bubble[]      말풍선
  winnerId      Long | null   판이 끝났을 때만
```

### 4.0 옵션은 `game` 이 아니라 방에 있다 (2026-08-23 정정)

처음에 `turnSeconds`·`noReuse` 를 `game` 안에 뒀는데 **한 판도 안 한 방은 `game` 이 `null`
이라 실을 자리가 없다.** 방장이 7초를 골라도 브로드캐스트에 안 실려, 화면이 완전 제어
컴포넌트라 **방장 본인의 라디오까지 3초로 되돌아간다.** 누른 게 씹힌 것처럼 보인다.

"진행 중인 판의 굳은 규칙"과 "다음 판에 쓸 선택"을 나눠 양쪽에 두는 방법도 있는데 **굳은 쪽을
읽는 화면이 없다.** 카운트다운 바는 `turnEndsAt - serverNow` 로 길이를 잡고, 옵션 바는
진행 중에 안 그려진다. 진행 중에는 옵션 변경도 막혀 있어 두 값이 갈라지지도 않는다.

그래서 **방에만 둔다.** 진행 중에 다음 판 설정을 미리 바꿔두는 기능이 생기면 그때 나눈다.

**`players` 는 대기실 설계에서 한 글자도 바뀌지 않는다.** 게임 상태를 거기 섞으면 방(누가 앉아
있나)과 판(누가 살아 있나)이 한 덩어리가 된다.

**관전자는 따로 표시하지 않는다.** `players` 에 있고 `turnOrder` 에 없으면 관전이다. 필드를
더하면 두 곳이 어긋날 수 있다.

**`usedWords` 를 내려보낸다.** 재사용 금지가 켜진 방에서 이미 나온 단어를 화면에 안 보여주면
기억에만 의존하게 된다. 기회가 3번(3초에서는 사실상 1번)뿐이라 불공평하다. 20턴이면 20개다.

**`turnOrder` 는 좌석 순서가 아니다.** 좌석은 `players` 순서 그대로고 판이 끝날 때까지 안
움직인다. 순서는 랜덤이라 유리한 자리가 없다.

### 4.1 말풍선

```
Bubble
  userId    Long
  word      String
  state     PENDING | PASS | FAIL
  verified  boolean          PASS 일 때만 뜻이 있다
  reason    String | null    FAIL 일 때만
```

| `reason` | |
|---|---|
| `NOT_THREE_LETTERS` | 세 글자가 아니다 |
| `NOT_CHAINED` | 앞 단어와 안 이어진다 |
| `ALREADY_USED` | 이미 나왔다 |
| `NOT_IN_DICTIONARY` | 사전에 없는 명사다 |

**틀린 이유를 실어 보낸다.** 왜 안 됐는지 모르면 남은 기회를 같은 실수로 쓴다.

**`verified: false` 는 사전을 못 써서 낱말 검사를 건너뛰었다는 뜻이다.** 전체 그림 6.7 대로
통과시키되 화면에 표시한다. 조용히 통과시키면 검사가 꺼진 줄 모른다.

**말풍선은 다음 제출이 올 때까지 산다.** 턴이 넘어갈 때가 아니다.

처음에는 "턴이 넘어가면 비운다"로 잡았는데 **통과 말풍선이 화면에 안 보인다.** 통과하면 곧바로
턴이 넘어가므로 `PASS` 가 1ms 살고 사라진다 — 오답은 턴이 유지돼 보이는데 성공만 안 보인다.
낸 사람이 통과했는지 확인할 방법이 화면에 없어진다.

**새 제출이 오면 이전 것을 갈아치운다.** 그러면 앞사람의 통과 단어가 다음 사람이 낼 때까지
연단 위에 남는다. `bubbles` 에 담기는 것은 늘 **가장 최근 제출 하나**다.

### 4.1.1 판이 끝나면 차례 관련 값이 `null` 이다

**`turnUserId` 와 `turnEndsAt` 은 판이 끝나면 `null` 로 온다.** 아무의 차례도 아니기 때문이다.

마지막 턴 값을 남겨두면 **결과 화면에 이미 지난 시각으로 카운트다운 바가 그려진다.**
`turnEndsAt - serverNow` 가 음수가 된다.

화면은 `winnerId` 로 먼저 갈라 그리므로 정상 경로에서는 읽지 않는다. 그래도 **타입을 nullable
로 둔다** — 나중에 무심코 읽는 코드가 생기면 컴파일러가 먼저 잡는다.

### 4.1.2 `turnOrder` 에는 이미 나간 사람이 남는다

게임 중에 나간 사람은 `players` 에서 빠지지만 **`turnOrder` 에는 남는다.** 판이 시작될 때 굳은
명단이라 중간에 바꾸면 "지금 몇 번째 차례"가 흔들리고, `eliminated` 에 남은 id 가 어디에도
없는 값이 된다.

**그래서 무대는 `turnOrder` 가 아니라 `players` 를 돈다.** `turnOrder` 로 돌면 `players` 에서
이름을 못 찾아 `undefined` 가 나온다. 나간 사람은 연단이 사라지는 것으로 충분하다 — 방을 떠난
사람이니 자리가 없는 게 맞다.

### 4.2 게임이 끝난 상태를 따로 표현하지 않는다

```
status: PLAYING, game: {...}            진행 중
status: WAITING, game: { winnerId }     결과 화면 (다음 시작 전까지)
status: WAITING, game: null             아직 한 판도 안 한 방
```

`lastWinner` 같은 필드를 더하지 않고 **`status` 와 `game` 의 조합**으로 읽는다. 중간에 들어온
사람도 같은 화면을 본다.

## 5. STOMP 계약

대기실 계약을 그대로 두고 **더하기만** 한다. 목적지도 방 상태 브로드캐스트도 바뀌지 않는다.

### 5.1 전송 — 새로 생기는 둘

| 목적지 | 본문 | 권한 |
|---|---|---|
| `/app/rooms/{id}/options` | `{"turnSeconds":3,"noReuse":true}` | 방장, `WAITING` 일 때만 |
| `/app/rooms/{id}/answer` | `{"word":"과일"}` | 지금 차례인 사람 |

`turnSeconds` 는 **3 · 5 · 7 만 받는다.** 다른 값은 거절한다.

**본문에 `content-type: application/json` 을 붙인다.** STOMP 클라이언트가 자동으로 붙여주지
않는다.

### 5.2 브로드캐스트

`/topic/rooms/{id}` 로 **방 상태 전체**를 보낸다. 조각내지 않는다.

```json
{
  "id": 7, "name": "점심내기 한판", "status": "PLAYING",
  "hostId": 2, "capacity": 10,
  "serverNow": 1787420000000,
  "turnSeconds": 3,
  "noReuse": true,
  "players": [ { "userId": 2, "name": "김성호", "avatar": "MALE", "ready": true } ],
  "game": {
    "currentWord": "사과",
    "turnUserId": 5,
    "turnEndsAt": 1787420003000,
    "triesLeft": 2,
    "usedWords": ["사과"],
    "turnOrder": [2, 5, 9],
    "eliminated": [9],
    "bubbles": [ { "userId": 5, "word": "과일", "state": "PENDING" } ],
    "winnerId": null
  }
}
```

**답을 받는 즉시 한 번, 판정이 끝나면 다시 브로드캐스트한다.** 클라이언트가 자기 말풍선을 혼자
그리면 상태의 주인이 둘이 된다. 그리고 이 편이 게임에도 낫다 — 남들도 "누가 뭔가 냈다"를 즉시
본다.

### 5.3 오류 — 본인만 알면 되는 것

| `code` | |
|---|---|
| `NOT_YOUR_TURN` | 내 차례가 아닌데 냈다 |
| `GAME_NOT_PLAYING` | 진행 중이 아닌데 냈다 |
| `NOT_ROOM_HOST` | 방장이 아닌데 옵션을 바꿨다 |
| `INVALID_TURN_SECONDS` | 3 · 5 · 7 이 아니다 |
| `GAME_ALREADY_PLAYING` | 진행 중인데 옵션을 바꿨다 |

**오답은 여기로 가지 않는다.** 말풍선에 떠서 모두가 본다 — 틀린 답이 보이는 게 이 게임의
재미다.

## 6. 3초가 만드는 제약 셋

### 6.1 클라이언트 시계 오차가 드러난다

`turnEndsAt` 을 절대 시각으로 내리는 것은 네트워크 지연을 피하려는 것이고 그건 맞다. 그런데
절대 시각은 **양쪽 시계가 맞다는 전제** 위에 선다. 브라우저 시계는 몇 초씩 틀어져 있는 일이
흔하다.

15초 턴이면 0.5초 오차가 3%라 안 보인다. **3초 턴에서는 17%다.** 카운트다운이 0을 지났는데 아직
낼 수 있거나, 1초 남았는데 이미 잡힌다.

**브로드캐스트에 `serverNow` 를 같이 싣는다.** 클라이언트는 받은 순간
`offset = serverNow - 내 시계` 를 구해 그만큼 보정해 그린다. 절대 시각의 장점(드리프트 없음)은
그대로 두고 시계 오차만 없앤다. 남는 것은 편도 지연 50ms 정도로 3초에서도 무시할 만하다.

**판정은 어차피 서버가 한다.** 화면의 카운트다운은 보여주기용이라, 보정은 억울함을 없애는
것이지 규칙을 바꾸지 않는다.

### 6.2 한글 조합 중 Enter 가 기회를 통째로 먹는다

마지막 글자를 조합하는 중에 Enter 를 치면 **조합만 확정되고 제출은 안 된다.** 한 번 더 쳐야
하는데 3초에서는 그 사이에 턴이 끝난다.

**조합 중 Enter 를 받으면 확정 직후 그 값으로 바로 제출한다.** `compositionend` 에서 대기 중인
제출을 흘려보낸다. 두 번 치게 만들지 않는다.

`isComposing` 을 보고 그냥 무시하는 흔한 처리로는 이 문제가 안 풀린다 — 무시하는 것이 곧 두 번
치게 만드는 것이다.

### 6.3 사전 타임아웃이 1초 아래여야 한다

3초 턴에 사전이 2초를 먹으면 판정이 턴보다 늦게 나온다. 타임아웃을 짧게 걸고, 넘으면 전체 그림
6.7 대로 **통과 + `verified: false`** 다.

**짧은 턴을 고르면 미확인 통과가 늘어난다.** 이것이 3초를 고른 실제 대가다. 화면에 표시하므로
숨기지는 않는다.

## 7. 화면

무대는 대기실 것을 그대로 쓴다. `Stage` 와 `PlayerPodium` 에 **선택적 props 를 더한다** —
좌석 배치를 두 벌 만들면 6명 경계 같은 규칙이 두 곳에서 어긋난다.

```
┌──────────────────────────────────────────────┐
│  점심내기 한판                    3/10  나가기  │
├──────────────────────────────────────────────┤
│                    사 과                      │  이어갈 단어
│                                              │
│      🧍    🧍    🧍    🧍    🧍               │
│     이영희  박철수  강민지  최민수  정다은        │
│      흐림   흐림   회색    흐림   흐림          │
│                                    ╭──────╮  │
│    🧍    🧍    🧍    🧍    🧍      │ 과일  │  │  말풍선
│   김성호  오세훈  한지우  윤서준  서지훈 ╰──────╯  │
│           밝음                               │  스포트라이트
├──────────────────────────────────────────────┤
│ ▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░ │  카운트다운
│ [ 과로 시작하는 세 글자        ] [내기] 2번 남음 │
└──────────────────────────────────────────────┘
```

### 7.1 카운트다운은 숫자가 아니라 바다

3→2→1 은 읽는 데 시간이 걸린다. 화면 폭을 가로지르는 바는 주변시로 잡혀서, 치는 사람은
입력칸을 보면서도 남은 시간을 안다.

### 7.2 결과 화면은 대기실로 완전히 돌아간다

`ready` 가 초기화되므로 다시 시작하려면 사람들이 준비를 눌러야 한다. 그러면 **승자 배너는
발표만 하고, 시작은 평소의 준비 바가 맡는다.** 배너에 `다시 시작` 을 따로 두면 준비가 안 된
동안 비활성으로 떠 있는 버튼이 둘이 되어 어느 것을 눌러야 할지 알 수 없다.

**무대도 대기실 모드로 돌아간다 — `game` 을 넘기지 않는다.**

처음에는 결과 화면에서도 무대에 `game` 을 넘겨 승리·탈락 배지를 그렸다. **두 가지가 깨진다.**

- 게임 모드 연단은 `준비` 배지를 감춘다. 준비를 눌러도 무대에 아무 변화가 없어, 사람들이
  버튼이 먹었는지 알 수 없다
- **`탈락` 배지가 남는다.** 판이 끝나면 아무도 탈락 상태가 아닌데, 다음 판을 시작할 방장이
  회색으로 죽어 보인다

승자는 배너가 이미 이름으로 알린다. 무대까지 지난 판을 그릴 이유가 없다.

### 7.3 입력칸은 내 차례가 아니어도 자리를 지킨다

비활성으로 두고 문구만 바꾼다. **3초마다 레이아웃이 튀면 눈이 못 따라간다.**

내 차례가 되면 **자동으로 포커스**가 간다. 마우스로 클릭할 시간이 없다. 제출하면 칸을 비운다.

| 내 상태 | 하단 |
|---|---|
| 내 차례 | 입력칸 활성 + 남은 기회 |
| 남의 차례 | 비활성, `이영희 님 차례` |
| 탈락 | `탈락했습니다` |
| 관전 | `다음 판부터 참가합니다` |
| 결과 화면 | 승자 배너 + 평소의 옵션·준비 바 |

### 7.4 연단은 셋으로 갈린다

**밝음**(내 차례) · **흐림**(살아있지만 남의 차례) · **회색**(탈락).

**탈락을 연단만으로 알리지 않는다.** 자기 연단은 화면 어딘가에 있고 안 보고 있을 수 있어서,
하단 바가 같이 바뀐다.

### 7.5 접근성

- 이어갈 단어와 차례 바뀜은 `role="status"` 로 읽힌다. `alert` 이 아닌 이유는 3초마다
  스크린리더가 읽던 것을 끊어먹기 때문이다
- 말풍선의 통과·오답은 **색만으로 갈리지 않는다** — 표시와 문구를 같이 단다
- **카운트다운 바는 `reduced-motion` 에서도 끄지 않는다.** 장식이 아니라 정보다.
  스포트라이트 밝기 전환과 말풍선 등장은 끈다

## 9. 폐기한 대안

| 대안 | 왜 안 하나 |
|---|---|
| 게임 전용 토픽 | 참가자 목록과 턴이 따로 와 순서가 뒤집히면 화면이 어긋난다 |
| `players[].alive` | 방 상태와 판 상태가 한 덩어리가 된다 |
