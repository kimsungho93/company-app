# 회원가입 화면 설계

작성일: 2026-08-12
대상: `front/company-app`
선행 문서: [2026-08-10-login-screen-design.md](2026-08-10-login-screen-design.md)

## 1. 배경

로그인 화면 하나로 시작했지만 계정을 만들 방법이 없다. 화면이 둘이 되면서 **라우터 도입**과 **요청 계층 방식**이라는 미뤄둔 결정 두 개가 함께 걸린다.

백엔드(`backend/company-backend`)는 Gradle 멀티모듈로 재구성됐고 `user` 모듈이 생겼지만 **아직 `build.gradle` 만 있는 껍데기**다. 인증 엔드포인트도 JWT 필터도 없다. 따라서 회원가입 API 경로는 미정으로 두고 화면을 먼저 만든다.

## 2. 결정 요약

| 항목 | 결정 | 이유 |
|---|---|---|
| 가입 방식 | 사내 이메일(`@ibslab.com`) 제한 자체 가입 | 관리자 부담 없이 외부인 가입을 막는다 |
| 라우팅 | react-router. `AuthLayout` 을 레이아웃 라우트로 | URL 공유·뒤로가기가 동작하고, 웨이퍼가 재마운트되지 않는다 |
| 폼 | 이메일 · 이름 · 비밀번호 · 비밀번호 확인 | 사번·부서는 인사 데이터가 없어 지금은 뺀다 |
| 비밀번호 정책 | 길이만(8~20자), 복잡도 조합 없음 | 아래 4장 참고 |
| 가입 성공 후 | 자동 로그인하지 않고 로그인 화면으로 | 계약이 단순하고, 이메일 인증을 붙여도 흐름이 안 깨진다 |
| API 경로 | **미정.** mock 으로 두고 상수 한 곳에 모음 | 백엔드에 엔드포인트가 없다 |
| 요청 계층 | 현재 방식 유지 → 백엔드 연결 시 **RTK Query** 로 이전 | 아래 8장 참고 |
| `pages` 레이어 | 아직 만들지 않음 | 두 화면 모두 auth 도메인이라 레이어를 더해도 경계가 안 생긴다 |

## 3. 라우팅과 파일 배치

```
/         → /login 로 리다이렉트
/login    → LoginPage
/signup   → SignupPage
그 외      → /login 로 리다이렉트
```

```
src/
├── app/
│   ├── App.tsx                 # RouterProvider
│   └── routes.tsx              # 라우트 정의
└── features/auth/
    ├── ui/
    │   ├── AuthLayout.tsx      # 웨이퍼 + 카드 골격. <Outlet /> 을 품는다
    │   ├── LoginPage.tsx   + LoginForm.tsx     # LoginForm 은 수정 (4장 참고)
    │   └── SignupPage.tsx  + SignupForm.tsx
    ├── model/
    │   ├── validateSignup.ts   # 가입 전용 검증 (기존 validate.ts 와 분리)
    │   └── useSignup.ts
    ├── api/
    │   └── signup.ts
    └── index.ts
```

### AuthLayout 을 레이아웃 라우트로 두는 이유

`WaferCanvas` 는 `AuthLayout` 이 소유하고 각 페이지는 `<Outlet />` 자리에 들어간다.

**각 페이지가 캔버스를 따로 들면 `/login` ↔ `/signup` 을 오갈 때마다 캔버스가 언마운트·재마운트되어 노광 인트로가 다시 재생된다.** 세션당 1회 규칙이 있어 실제 재생은 막히지만, 캔버스 재빌드(다이 3,600개 재계산 + 폰트 샘플링)는 그대로 일어나 화면이 깜빡인다. 레이아웃 라우트로 두면 DOM 이 유지되어 이 비용이 없다.

## 4. 회원가입 폼

### 필드와 검증

| 필드 | 규칙 | `autoComplete` |
|---|---|---|
| 이메일 | 형식 검사 + **`@ibslab.com` 도메인만**(대소문자 무시) | `email` |
| 이름 | 앞뒤 공백 제거 후 **2자 이상 10자 이하** | `name` |
| 비밀번호 | **8자 이상 20자 이하.** 공백도 유효한 문자라 `trim` 하지 않는다 | `new-password` |
| 비밀번호 확인 | 비밀번호와 일치 | `new-password` |

이메일은 **형식을 먼저 보고, 통과한 경우에만 도메인을 본다.** 순서가 반대면 `abc` 를 입력했을 때 "회사 이메일로만 가입할 수 있습니다"가 떠서 무엇이 잘못됐는지 알기 어렵다.

비밀번호 필드에는 입력 전부터 `8~20자` 헬프 텍스트를 띄운다. 규칙을 모르고 틀리는 것은 회원가입에서 가장 흔한 실패 경로다.

검증 시점은 로그인과 같다 — **blur 시점, 그리고 한 번 제출한 뒤부터는 입력 중에도** 갱신한다.

### 기존 컴포넌트에 필요한 변경

**`shared/ui/TextField` 에 `help` prop 을 추가해야 한다.** 지금은 `error` 와 `aside` 만 받는다.

> **구현 중 조정** — 처음에는 오류와 헬프를 함께 띄우고 `aria-describedby` 에 두 id 를 이어 붙이려 했다. 그런데 오류 문구가 이미 규칙을 담고 있어서(`비밀번호는 8자 이상 20자 이하로 입력해 주세요`) `8~20자` 를 함께 띄우면 같은 말이 두 번 나온다. **오류가 있으면 오류가 헬프를 대체**하고, `aria-describedby` 는 그때 렌더된 쪽을 가리킨다.

**`LoginForm` 도 수정이 필요하다.** 가입 후 리다이렉트로 넘어온 `location.state` 를 읽어 이메일을 채우고 성공 배너를 띄운다. 이때 기억된 이메일(`rememberedEmail`)보다 **넘어온 이메일이 우선**한다 — 방금 가입한 주소로 로그인하려는 의도가 명확하다.

### 비밀번호 복잡도 규칙을 넣지 않는 이유

NIST SP 800-63B 는 복합 문자 규칙(대·소문자, 숫자, 특수문자 강제)을 **권장하지 않는다.** 규칙을 걸면 사용자는 `Ibslab2026!` 같은 예측 가능한 패턴을 만든다. 엔트로피는 거의 오르지 않는데 기억은 어려워져 재사용과 메모로 이어진다.

같은 노력은 서버 쪽 방어에 쓰는 것이 훨씬 효과적이다 — 유출된 비밀번호 목록 대조, rate limiting, argon2id/bcrypt 해싱.

**프론트 검증은 전부 UX 용이며 보안을 책임지지 않는다.** 개발자 도구로 우회된다. 서버가 같은 규칙을 독립적으로 검증해야 한다.

> **상한 20자에 대한 기록** — NIST 는 최소 64자까지 허용할 것을 권한다. 20자 상한은 비밀번호 관리자가 생성하는 24~32자 암호를 거부한다. 이 점을 알린 뒤 사용자가 20자를 재확인했다. bcrypt 의 72바이트 제한 안이라 잘림 문제는 없다. 사내 정책이 바뀌면 `validateSignup.ts` 의 상수 하나만 고치면 된다.

### 오류 문구

| 상황 | 문구 |
|---|---|
| 이메일 형식 | 이메일 형식이 올바르지 않습니다. |
| 도메인 불일치 | 회사 이메일(@ibslab.com)로만 가입할 수 있습니다. |
| 이름 길이 | 이름은 2자 이상 10자 이하로 입력해 주세요. |
| 비밀번호 길이 | 비밀번호는 8자 이상 20자 이하로 입력해 주세요. |
| 확인 불일치 | 비밀번호가 일치하지 않습니다. |
| 409 중복 | 이미 가입된 이메일입니다. |
| 네트워크·5xx | 해당 오류 메시지 (폼 상단 `role="alert"`) |

## 5. 가입 성공 후 흐름

`navigate('/login', { state: { email, justSignedUp: true } })`

로그인 화면은 이 상태를 받아 **이메일을 미리 채우고 성공 배너를 띄운다.** 배너는 오류가 아니므로 `role="status"` 를 쓴다(`alert` 는 오류용이다).

URL 쿼리 대신 라우터 state 를 쓰는 이유는 이메일이 주소창에 남지 않게 하기 위해서다. 새로고침하면 state 가 사라져 배너도 없어지는데, 이는 의도한 동작이다.

## 6. API 계약 — 미정

경로가 확정되지 않았으므로 상수로 분리한다.

```ts
// features/auth/api/signup.ts
const SIGNUP_PATH = '/api/auth/signup'   // 백엔드 확정 시 여기만 수정
const USE_MOCK = true
```

가정하는 계약은 다음과 같다. 백엔드 구현 시 이 문서를 함께 갱신한다.

```
POST {SIGNUP_PATH}
  요청  { email: string, name: string, password: string }
  201   (본문 없음)
  409   { code: "EMAIL_ALREADY_EXISTS" }
  400   { code: "INVALID_EMAIL_DOMAIN" }
```

### mock 규칙

- `taken@ibslab.com` → 409 중복
- `error@ibslab.com` → 네트워크 오류
- 그 외 → 800ms 후 성공

## 7. 계정 열거에 대한 트레이드오프

로그인 401 은 어느 쪽이 틀렸는지 알려주지 않는다(계정 열거 방지). **그런데 회원가입 409 는 "이미 가입된 이메일"이라고 알려준다.** 이는 해당 주소의 계정 존재를 노출한다.

그럼에도 표시하기로 한 이유는 두 가지다. 도메인이 `@ibslab.com` 으로 제한되어 열거 대상이 사내 구성원으로 좁고, 안내가 없으면 사용자가 가입이 안 되는 이유를 알 수 없다.

**외부 공개 서비스가 되면 이 결정을 다시 봐야 한다.** 그때의 대안은 "가입 안내 메일을 보냈습니다"로 통일하고 실제 분기는 메일 내용에서 처리하는 방식이다.

## 8. 요청 계층 로드맵

Redux Toolkit 을 도입하기로 했으므로 서버 상태는 **RTK Query** 로 간다. `@reduxjs/toolkit/query` 는 별도 패키지가 아니어서 의존성이 늘지 않고, Redux 를 쓰면서 TanStack Query 를 얹으면 상태의 거처가 두 곳으로 갈린다.

다만 **지금은 도입하지 않는다.** 백엔드 응답 형태를 모르는 상태에서 계약을 짜면 두 번 짜게 된다. 회원가입 화면은 요청 계층과 무관하게 같은 모양이며, 바뀌는 것은 `features/auth/api/*.ts` 내부뿐이다.

도입 시 구조는 다음과 같다.

```
app/store.ts                    configureStore
shared/api/baseQuery.ts         fetchBaseQuery + 401 재발급 래핑
shared/api/baseApi.ts           createApi({ endpoints: () => ({}) })
features/auth/api/authApi.ts    baseApi.injectEndpoints({ login, signup })
```

`shared/api/baseApi` 를 빈 껍데기로 두고 각 feature 가 `injectEndpoints` 로 주입해야 `shared → features` 역방향 의존이 생기지 않는다.

**기존 `reissue.ts` 의 "진행 중인 Promise 공유" 로직은 그대로 재사용한다.** RTK Query 의 동시 401 처리는 보통 `async-mutex` 로 푸는데, 우리 구현이 이미 같은 문제를 해결하고 있다.

### access token 을 Redux store 에 넣지 말 것

RTK 도입 시 가장 흔한 실수다.

- Redux DevTools 에 토큰이 그대로 노출된다
- `redux-persist` 를 붙이는 순간 localStorage 로 새어나가, 메모리에만 두기로 한 결정이 무너진다

`shared/api/tokenStore` 의 모듈 스코프 방식을 유지하고, store 에는 "로그인됨/아님" 같은 파생 상태만 둔다.

## 9. 접근성

로그인 화면과 같은 원칙을 따른다. 회원가입에서 추가로 지킬 것:

- 비밀번호 확인 필드도 `autoComplete="new-password"` 다. `current-password` 를 쓰면 비밀번호 관리자가 기존 암호를 채운다
- 헬프 텍스트(`8~20자`)는 `aria-describedby` 로 입력과 연결한다. 오류가 생기면 오류 메시지로 교체하지 말고 **둘 다 연결**한다
- 성공 배너는 `role="status"`, 오류는 `role="alert"`
- 필드가 4개로 늘어 카드가 길어진다. 세로 스크롤이 생기는지 실측하고, 생긴다면 페이지 스크롤로 처리한다(카드 내부 스크롤은 만들지 않는다)

## 10. 테스트

| 대상 | 케이스 |
|---|---|
| `validateSignup` | 도메인 통과·거부, 대소문자 무시, 이름 경계값(1·2·10·11자), 비밀번호 경계값(7·8·20·21자), 확인 일치·불일치 |
| `useSignup` | 성공, 409 중복, 네트워크 실패, 오류 해제 |

라우팅과 화면 전환은 자동 테스트하지 않는다. 웨이퍼 캔버스와 마찬가지로 비용 대비 이득이 낮다.

## 11. 범위 밖

- 이메일 인증(verification) 메일 — 백엔드에 메일 발송 수단이 없다
- 비밀번호 강도 미터 — 길이 규칙만 쓰기로 한 결정과 일관되게 뺀다
- 약관 동의 — 약관 문서 자체가 없다
- 사번·부서 — 인사 데이터와 연결할 방법이 없다
- 소셜 가입 — 백엔드에 OAuth 설정이 없다
- 비밀번호 찾기 화면 — 링크 자리만 있다

## 12. 후속 작업

- 백엔드 `user` 모듈에 회원가입·로그인 엔드포인트 구현
- 경로 확정 후 이 문서의 6장 갱신과 `SIGNUP_PATH` 수정
- RTK Query 도입 (8장)
- `springdoc-openapi` 도입 시 `openapi-typescript` 로 응답 타입 자동 생성 검토
