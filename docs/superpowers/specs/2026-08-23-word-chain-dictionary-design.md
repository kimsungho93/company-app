## 1. 범위

전체 그림의 **D** 다. C 에서 스텁으로 뚫어둔 사전 판정 자리에 표준국어대사전을 실제로 붙인다.

| 백엔드 | 프론트 |
|---|---|
| 표준국어대사전 실호출 | 소켓 거절 사유를 문구에 반영 |
| Caffeine 캐시 (확정된 결과만) | |
| 짧은 타임아웃 + 실패 시 통과 | |
| 연속 실패 시 로그 경고 | |
| 스텁 → 실제 어댑터 교체 | |

**계약이 바뀌지 않는다.** `verified` 도 `NOT_IN_DICTIONARY` 도 이미 흐르고 있고 화면이 둘 다
그린다. 스텁이 실제로 바뀌면 **`verified: true` 가 처음 나타나고 `NOT_IN_DICTIONARY` 가 처음
온다.** 그뿐이다.

**들어가지 않는 것** — 전적·통계, 채팅, 방 목록 실시간 갱신, 재연결.

## 2. 결정 요약

조사(`2026-08-22-dictionary-api-spike.md`)와 앞 스펙들이 대부분을 이미 정했다. D 에서 새로
정한 것만 적는다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 장애 감지 | **연속 실패 5회 → WARN 한 번, 복구 시 INFO 한 번** | 매번 남기면 로그가 넘친다. 전환에만 남기면 장애 구간이 괄호로 묶여 보인다 |
| 캐시 상한 | **`maximumSize(10_000)`** | 메모리 안전판이다. 할당량과는 무관하다 |
| 타임아웃 | **800ms** | 3초 턴에서 1초 아래여야 하고 소켓 왕복에 200ms 를 남긴다 |
| 판정 대기 표시 | **지금 것을 그대로 둔다** | 3.2 참고 |
| 프론트 계획 문서 | **쓰지 않는다** | 세 파일 30줄이다. 계획 비용이 구현 비용보다 크다 |

## 3. 프론트 — 소켓 거절 사유

### 3.1 지금은 사유를 통째로 버린다

서버가 SUBSCRIBE 를 거절할 때 ERROR 프레임에 사유를 싣는다.

```
ERROR
message: NOT_IN_ROOM

{"code":"NOT_IN_ROOM","message":"이 방의 참가자가 아닙니다."}
```

**`/user/queue/errors` 로는 올 수 없다** (백엔드 실측). 거절당한 세션은 브로커를 거치기 전에
닫히므로, 닫는 원인인 ERROR 프레임에 싣는 것이 유일하게 확실한 경로다.

화면은 지금 권한 거절이든 진짜 끊김이든 `연결이 끊어져 방에서 나왔습니다` 라고 같게 말한다.
거절인 경우 사실과 다르다.

**`shared/ws` 가 사유를 넘겨준다.**

```ts
onError: (reason?: { code: string; message: string }) => void
```

`onStompError(frame)` 에서 `frame.body` 를 JSON 으로 파싱해 넘긴다. 파싱이 안 되면 아무것도
넘기지 않고, `onWebSocketError` 는 애초에 사유가 없다.

**`shared` 는 여전히 도메인을 모른다.** `{code, message}` 는 이 프로젝트의 오류 형태이지
끝말잇기 개념이 아니다.

### 3.2 `useRoomSocket` 은 첫 사유만 남긴다

```ts
disconnected: { message: string | null } | null
```

`boolean` 을 객체로 바꾸면 **같은 값을 두 번 세팅하는 것이 더 이상 무해하지 않다.** 지금은
`setDisconnected(true)` 가 두 번 불려도 값이 같아 이펙트가 한 번만 도는데, 객체는 매번 새
참조라 두 번 이동한다.

```ts
onError: (reason) => setDisconnected((prev) => prev ?? { message: reason?.message ?? null })
```

**첫 사유가 이긴다.** 뒤에 오는 것은 무시한다.

### 3.3 문구는 페이지가 고른다

```tsx
state: { notice: disconnected.message ?? '연결이 끊어져 방에서 나왔습니다.' }
```

서버가 준 문구가 있으면 그것을 쓰고 없으면 기존 문구다. **문구를 `model` 에 두지 않는 이유는
거기가 화면 말투를 정하는 자리가 아니어서다.**

### 3.4 판정 대기 표시는 그대로 둔다

C 에서 만든 것 — 내 답이 `PENDING` 이면 입력칸을 잠그고 `확인 중…` 을 띄운다 — 으로 충분하다.

타임아웃이 800ms 라 **카운트다운 바가 0 에 닿은 채 머무는 구간은 마감 직전에 낸 경우에만**
생긴다. 그때도 입력칸이 잠기고 문구가 떠 있어 "내가 시간 초과된 건가"와 구분된다. 불확정
애니메이션을 더하는 것은 1초짜리 드문 구간을 위해 상태를 하나 더 만드는 일이다.

### 3.5 CONNECT 거절은 사유가 오지 않는다 (실측)

세션이 성립하기 전이라 서버가 돌려줄 통로가 없다. **토큰 만료로 거절된 것과 네트워크 끊김이
클라이언트에서 구분되지 않는다.**

지금은 영향이 없다 — 재연결을 안 하기로 정했으므로 어느 쪽이든 목록으로 보낸다. 연결 직전
`reissueOnce()` 가 만료를 미리 걷어내기도 한다. **재연결을 다시 논의하면 이 제약이 전제다.**

## 4. 백엔드 — 사전 판정

### 4.1 요청. 옵션은 절대 변하지 않는다

```
GET https://stdict.korean.go.kr/api/search.do
    ?key={KEY}&req_type=json&q={사용자가 친 그대로}
    &advanced=y&method=exact&pos=1&type1=word
```

**`advanced=y` 가 이 요청의 중심이다.** 없으면 `pos=1`(명사)과 `type1=word` 가 **조용히
무시되고**, 결과 0건과 오류도 안 갈린다.

**`num` 을 건드리지 말 것.** 10~100 만 유효한데 9 이하는 오류이고, 오류는 빈 본문이라 **없는
단어처럼 보인다.** "한 건만 필요하니 `num=1`" 이 그 함정이다.

**`q` 는 사용자 입력을 그대로 보낸다.** 표제어에는 붙임표가 붙어 오지만(`가가-례`) 검색은
붙임표 없는 형태가 맞다 — 정규화가 필요한 쪽은 응답이지 요청이 아니다.

### 4.2 응답. 파싱되면 질의가 성립한 것이다

```
본문이 파싱됨  →  질의 성공. total 을 읽어 있음/없음 확정  →  캐시한다
본문이 비었음  →  오류 (키·파라미터·한도 어느 쪽인지 모름)  →  캐시하지 않는다
타임아웃·네트워크 실패                                      →  캐시하지 않는다
```

**"확정"과 "확인 못 함"을 가르는 것이 전부다.** 없는 단어를 캐시하는 것 자체는 맞다 — 같은
오타가 반복되니 호출이 크게 준다. 문제는 **오류를 없음으로 착각하는 것**이다. 그러면 키가 죽은
동안 멀쩡한 단어가 하루치 오답으로 굳는다.

`total >= 1` 이면 통과다. 동음이의어는 별개 항목으로 오지만 세지 않는다.

**확인 못 함은 통과 + `verified: false`** 다 (전체 그림 6.7). 차단하면 멀쩡한 단어를 낸 사람이
턴을 잃고, 사전이 죽으면 아무도 게임을 못 한다.

### 4.3 캐시

| | |
|---|---|
| 구현 | Caffeine |
| 키 | **단어 하나.** 옵션이 상수라 섞을 필요가 없다 |
| 값 | 있음/없음 (확정된 것만) |
| TTL | 1일 |
| 상한 | `maximumSize(10_000)` |
| 동시 조회 | `get(key, loader)` 로 같은 단어의 중복 호출을 막는다 |

**상한을 두는 이유는 메모리지 할당량이 아니다.** 하루에 고유 단어 1만 개를 넘겼다면 이미 호출을
1만 번 한 것이고, 5만 한도에 한참 못 미친다. 축출이 할당량을 의미 있게 더 먹지 않는다.

### 4.4 타임아웃 800ms

3초 턴에 판정이 늦으면 게임 진행 스펙 4.5 대로 시간 초과가 된다. 1초 아래여야 하고, 소켓
왕복에 200ms 를 남겨 800ms 로 잡는다.

**캐시 히트는 사실상 0ms 라 타임아웃이 무는 것은 미스일 때뿐이다.** 초반에는 자주, 캐시가
데워지면 드물어진다.

**실측값 없이 정한 숫자였다.** 붙인 뒤 재보니 p95 681ms · 최대 767ms 로 예산 안에 들어와,
그대로 두기로 했다. 분포는 5.3 에 있다.

### 4.5 장애 감지는 상태가 바뀔 때만 남긴다

```
빈 본문 5회 연속  →  WARN 한 번
그 뒤 첫 성공     →  INFO 한 번
```

일일 5만을 넘기면 JSON 은 빈 본문으로 온다. 키가 죽었을 때도, 파라미터가 틀렸을 때도 같다.
**JSON 으로는 셋이 구분되지 않는다.** 게임 동작은 어느 쪽이든 같으므로 구분할 필요도 없고,
운영자가 "사전을 못 쓰는 상태"라는 것만 알면 된다.

**매번 남기면 로그가 넘친다.** 전환에만 남기면 로그에 장애 구간이 괄호로 묶여 보인다.
5회로 잡은 것은 한 번의 일시적 실패로 경고가 뜨지 않게 하려는 것이다.

**화면은 안 바뀐다.** 플레이어에게는 말풍선의 `사전 확인 못 함` 이 그대로 신호다.

### 4.6 스텁 → 실제

포트는 C 에서 이미 뚫었다. 프로필로 가른다 — **로컬·테스트는 스텁, 운영만 실제.**

**테스트가 외부 API 를 때리면 안 된다.** 느려지고, 저쪽이 죽으면 같이 죽고, 할당량도 먹는다.
키가 사용자당 하나라 개발용·운영용을 나눌 수도 없다. 조사 때 받은 실제 응답이 문서에 있으니
그것을 픽스처로 쓴다.

## 5. 검증

**실연동은 배포해야만 검증된다.** 로컬이 늘 스텁이기 때문이다. 앞 단계들처럼 올린 뒤 브라우저에서
확인한다.

| 확인할 것 | 판별점 | 결과 (2026-08-23 실측) |
|---|---|---|
| 실재 단어 | `사전 확인 못 함` 이 안 뜬다 | 확인됨 — `대나무`·`기찻길`·`무성의` 모두 |
| 명사가 아닌 것 | `사전에 없는 명사입니다` | 확인됨 — `다르다` 거절 |
| 캐시 | 서버 로그에 `사전 조회` 줄이 한 번만 | 확인됨 — 두 번 제출에 호출 한 번 |
| 첫 호출 지연 | 800ms 예산 안 | 확인됨 — 5.3 |
| 소켓 거절 문구 | 3장 | 미확인 — 정상 흐름에서는 안 나온다 |

**`pos=1` 확인이 중요하다.** `advanced=y` 를 빠뜨리면 조용히 무시되어, 명사 필터를 걸었다고
생각했는데 안 걸린 채로 동작한다. 동사·형용사가 통과하면 그것이다.

**`NOT_NOUN` 도 캐시된다.** 두 번째 제출에 같은 오답 문구가 떴는데 사전 호출은 없었다.
"없음"으로 확정된 것이라 캐시에 들어가는 게 맞다.

### 5.1 사전까지 가려면 싼 검사 셋을 먼저 통과해야 한다

`Game.ruleBroken()` 이 **글자 수 → 끝말 → 중복** 을 먼저 보고, 셋 다 통과해야 사전을 부른다.

- **동사는 3글자여야 한다.** `먹다` 는 `NOT_THREE_LETTERS` 로 잘려 사전을 거치지 않는다.
  `-르다` 로 끝나는 것이 가장 흔하다 — `다르다`·`고르다`·`자르다`·`지키다`
- **같은 단어 재제출은 `noReuse` 가 꺼져 있어야 한다.** 기본값이 `false` 라 보통은 그대로 된다

거절된 단어는 `usedWords` 에 안 들어가고 `currentWord` 도 안 바뀌므로, **오답을 두 번 내면
같은 단어가 사전까지 두 번 간다.** 캐시를 보는 자리가 여기다.

**오답은 턴을 안 넘기고 시도만 하나 줄인다.** 한 턴에 3번이니 동사·동사·명사로 한 번에 다
볼 수 있다. 다만 **`endsAt` 은 재시도해도 안 늘어난다** — 3번이 한 턴 시간을 나누어 쓰므로
3초로는 안 되고 7초로 올려야 한다.

### 5.2 캐시는 화면으로 못 잰다 (함정)

말풍선이 바뀌는 걸 기다려 시간을 재면 **직전 판정과 구분이 안 된다.** 2차 제출 직후에도
화면에는 1차의 말풍선이 그대로 남아 있고, 같은 단어라 글자로는 갈리지 않는다. 실제로 이것에
걸려 `1ms` 를 읽었는데, 그건 DOM 을 한 번 읽은 시간이었다. 결론을 낸 것은 서버 로그다.

**그 로그는 지금 꺼져 있다.** 측정이 끝나 껐으므로(`9c7ed3e`) 다시 재려면 사전 어댑터의
로거를 DEBUG 로 켜야 한다. **켜지 않고 "줄이 없으니 캐시"라고 읽으면 틀린다** — 애초에
아무 줄도 안 남는다.

### 5.3 응답 시간 — 800ms 는 측정이 지지한다

```
표본 35   최소 155   p50 358   p90 622   p95 681   최대 767
타임아웃 0건 · UNVERIFIED 0건
```

**콜드 스타트는 실재한다.** 배포 후 첫 호출이 **767ms** 였다. 브라우저에서 본 464ms 는
연결이 데워진 뒤라 낮게 나온 것이고, 여기에 소켓 왕복 140ms 가 더해진 값이다.

p95 가 681ms 라 여유가 120ms 뿐이다. 그래도 넘어가면 통과 + `verified: false` 라 게임이
안 깨지고, 3초 턴 때문에 1초 위로는 못 올린다. **근거 없이 정한 숫자였는데 측정이 그 값을
지지했다.**

## 6. 폐기한 대안

| 대안 | 왜 안 하나 |
|---|---|
| XML 로 요청 | `advanced=y` 만 붙으면 JSON 도 0건과 오류가 갈린다. XML 이 더 주는 건 로그용 오류 코드뿐인데 대가가 파서 의존성이다 |
| 빈 본문을 "없음"으로 캐시 | 키가 죽은 동안 멀쩡한 단어가 하루치 오답으로 굳는다 |
| 판정 불가일 때 차단 | 멀쩡한 단어를 낸 사람이 턴을 잃고, 사전이 죽으면 아무도 게임을 못 한다 |
| 한도 초과를 XML 재질의로 구분 | 게임 동작이 어느 쪽이든 같다. 운영자는 "못 쓰는 상태"만 알면 된다 |
