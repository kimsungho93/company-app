## 1. 범위

전체 그림의 **B** 다. 방에 들어간 뒤부터 게임이 시작되기 직전까지.

| 들어감 | 안 들어감 |
|---|---|
| 소켓 연결·인증 | 게임 진행 (턴·타이머·판정) — C |
| 참가자 목록 실시간 갱신 | 사전 판정 — D |
| 아바타 선택 (남·여) | 관전자 — 게임이 있어야 성립한다 |
| 준비 ⇄ 대기 | 채팅 |
| 방장 양도 | |
| 나가기 · 연결 끊김 | 방 목록 실시간 갱신 (`/topic/rooms`) |
| 무대 배치 (2단 계단) | |

**방 목록 실시간 갱신은 A 에 이어 여기서도 미룬다.** 목록 화면이 소켓을 하나 더 여는 구조가
되어 방 화면과 연결 수명이 얽힌다. 그때까지 목록은 화면에 들어올 때와 `invalidatesTags` 로만
갱신된다 — 옆 사람이 방을 만들면 새로고침해야 보인다. C 가 끝나고 다시 본다.

## 2. 결정 요약

| 항목 | 결정 | 이유 |
|---|---|---|
| 무대 | **2단 계단** (뒷줄 5 · 앞줄 5) | 한 줄이면 10명일 때 아바타가 34px 로 줄어 얼굴이 뭉개지고 이름이 잘린다 |
| 스포트라이트 | 자리는 그대로, **밝기만** 바뀐다 | 차례마다 아바타가 이동하면 3초 안에 움직임이 겹쳐 정신없다 |
| 아바타 | 남·여 2종, **방 안에서 선택** | 방을 나가면 잊는다. 계정에 저장하지 않는다 |
| 시작 조건 | **2명 이상 + 전원 준비 + 방장이 시작** | 마지막 사람이 준비를 누르는 순간 자동 시작되면 손이 버튼 위에 있는 채로 판이 시작된다 |
| 방장의 준비 | 버튼이 없다. **`ready` 값은 사실대로 내려온다** | 표시를 위해 값을 속이면 양도 뒤 그 사람의 진짜 상태를 알 수 없다 |
| 구독 권한 | **SUBSCRIBE 를 서버가 검사한다** | 안 하면 누구나 남의 비밀방을 구독해 엿본다. 5.4 참고 |
| 채팅 | 없음 | 말풍선이 이미 대화처럼 보인다. 입력칸이 둘이면 어디에 치는지 헷갈린다 |
| 방 상태 전달 | **통째로 브로드캐스트** | 조각내면 순서가 뒤집혔을 때 화면이 어긋나고 재접속 복구가 어렵다 |
| 좌석 회수 | 소켓 끊김 = 퇴장. **연결 없는 좌석은 30초 후 회수** | 유령 인원이 정원을 먹는다 |
| 소켓 주소 | 운영은 **Railway 직접**, 개발은 프록시 | Netlify rewrite 가 Upgrade 헤더를 떨군다. 6.2 참고 |

## 3. 좌석의 수명 — 여기가 제일 헷갈린다

A 에서 만든 `POST /api/rooms/{id}/join` 이 **이미 참가자로 넣는다.** 소켓은 그 뒤에 붙는다.

```
① POST /rooms/{id}/join   비밀번호·정원 확인, players 에 추가
② 화면 이동 /games/word-chain/{id}
③ 소켓 연결 + /topic/rooms/{id} 구독
④ /app/rooms/{id}/enter   이 세션이 이 방의 것임을 서버에 알린다
⑤ 서버가 방 상태를 브로드캐스트
```

**④가 필요한 이유** — 서버가 "이 소켓이 끊기면 누구를 어느 방에서 빼야 하는가"를 알아야 한다.
구독만으로 추측하지 않고 명시적으로 받는다.

**①과 ④ 사이에 탭을 닫으면 좌석이 남는다.** 그래서 **30초 안에 ④가 오지 않으면 서버가
좌석을 회수한다.** 없으면 방 하나가 유령으로 채워져 못 쓰게 된다.

이미 방에 있는 사람이 새로고침하면 ①이 다시 불린다. `Room.join` 이 **이미 있으면 그대로
돌려주므로**(현재 구현) 중복 입장이 아니다.

## 4. 참가자 상태

현재 `Room` 은 참가자를 `Set<Long> players` 로 들고 있다. **사람마다 상태가 붙어야 한다.**

```
Player
  userId    Long
  name      String                 화면에 그릴 이름
  avatar    MALE | FEMALE | null   (아직 안 고름)
  ready     boolean
```

**`name` 이 반드시 와야 한다.** 프론트에는 사용자 목록이 없어 `userId` 만으로는 이름을 그릴 수
없다. 방 목록이 `hostName` 을 내려보내는 것과 같은 이유다.

서버는 여기에 `sessionId` 를 하나 더 붙여 끊긴 세션의 주인을 찾는다. **내려오지 않는다.**

**순서는 입장 순서다.** 지금 `LinkedHashSet` 이 지키고 있고, 방장이 나갈 때 "가장 먼저 들어온
사람에게 양도"하는 규칙이 그 순서에 기댄다. 바꾸지 말 것.

**`ready` 는 사실대로 내려보낸다.** 방장에게는 준비 버튼이 없으므로 대개 `false` 로 남아 있다.

처음에는 "방장은 항상 `true` 로 내려보낸다"로 잡았는데 **양도에서 깨진다.** 값을 속이면 방장이
양도한 순간 그 사람의 진짜 준비 상태를 서버가 알지 못한다. 값은 사실대로 두고, 시작 조건을
**"2명 이상이고, 방장을 뺀 전원이 준비"** 로 판정한다 — 서버와 화면이 같은 규칙을 쓴다.

**인원 조건이 따로 필요하다.** 방장 혼자면 "방장을 뺀 전원"이 빈 집합이라 준비 조건이 그냥
참이 되어 혼자 끝말잇기를 시작하게 된다. 서버는 어기면 `NOT_ENOUGH_PLAYERS` 를 낸다.

연단도 이미 방장이면 `방장`, 아니면 `준비` 를 그리므로 화면에 예외가 늘지 않는다.

**아바타를 안 고른 사람도 준비할 수 있다.** 고르지 않으면 남자 아바타로 그린다 — 준비를
막으면 "왜 시작이 안 되지"를 찾아 헤매게 된다.

## 5. STOMP 계약

### 5.1 구독

| 목적지 | 내용 |
|---|---|
| `/topic/rooms` | 방 목록 요약. A 의 `RoomSummary[]` 와 같은 모양 |
| `/topic/rooms/{id}` | 방 상태 전체 (아래) |
| `/user/queue/errors` | 나에게만 가는 오류 `{ code, message }` |

```json
// /topic/rooms/{id}
{
  "id": 7,
  "name": "점심내기 한판",
  "status": "WAITING",
  "hostId": 2,
  "capacity": 10,
  "players": [
    { "userId": 2, "name": "김성호", "avatar": "MALE",   "ready": true },
    { "userId": 5, "name": "이영희", "avatar": "FEMALE", "ready": false },
    { "userId": 9, "name": "박철수", "avatar": null,     "ready": false }
  ]
}
```

**`players` 순서가 곧 무대 배치 순서다.** 화면이 임의로 정렬하지 않는다 — 정렬하면 사람이
들어올 때마다 다른 사람들의 자리가 바뀐다.

### 5.2 전송

| 목적지 | 본문 | 권한 |
|---|---|---|
| `/app/rooms/{id}/enter` | 없음 | 참가자 |
| `/app/rooms/{id}/avatar` | `{ "avatar": "MALE" }` | 본인 |
| `/app/rooms/{id}/ready` | `{ "ready": true }` | 본인 (방장 제외) |
| `/app/rooms/{id}/transfer` | `{ "userId": 5 }` | 방장 |
| `/app/rooms/{id}/leave` | 없음 | 참가자 |
| `/app/rooms/{id}/start` | 없음 | 방장 |

**`ready` 는 토글이 아니라 값을 보낸다.** 토글이면 메시지가 한 번 유실됐을 때 화면과 서버가
영원히 반대가 된다.

**본문이 있는 메시지에는 `content-type: application/json` 헤더를 붙인다.** 없으면 서버가
레코드로 역직렬화하지 못한다. STOMP 클라이언트가 자동으로 붙여주지 않는다.

모든 메시지는 처리 후 **방 상태 전체를 브로드캐스트**한다. 응답을 따로 주지 않는다.

### 5.3 오류

| `code` | 상황 |
|---|---|
| `NOT_ROOM_HOST` | 방장이 아닌데 시작·양도 |
| `NOT_ALL_READY` | 전원 준비 전에 시작 |
| `NOT_ENOUGH_PLAYERS` | 방장 혼자 시작 |
| `NOT_IN_ROOM` | 그 방의 참가자가 아님 |
| `ROOM_NOT_FOUND` | |

`/user/queue/errors` 로 **그 사람에게만** 보낸다. 남의 화면에 뜰 일이 아니다.

### 5.4 구독을 서버가 막아야 한다

**STOMP 는 SUBSCRIBE 를 자동으로 검사하지 않는다.** 소켓만 붙일 수 있으면 누구나
`SUBSCRIBE /topic/rooms/7` 로 남의 비밀방 참가자 목록과 진행 상황을 계속 받아볼 수 있다.
`POST /join` 의 비밀번호 검사를 통째로 우회한다.

**서버가 SUBSCRIBE 프레임에서 방 id 를 뽑아 그 사람이 참가자인지 확인해야 한다.**
`/app/rooms/{id}/enter` 도 마찬가지다 — 안 보면 REST join 을 건너뛰고 바로 방에 들어앉는다.

이건 화면 정리가 아니라 **접근 제어**다. 방 비밀번호가 장식이 되느냐 아니냐가 여기서 갈린다.

## 6. 인증과 연결

access token 을 **CONNECT 프레임 헤더**에 실어 보내고 서버가 검증해 `Principal` 을 세운다.

**그래서 핸드셰이크 경로(`/api/ws`)는 Spring Security 에서 열려 있어야 한다.** 브라우저의
`new WebSocket(url)` 은 헤더를 붙일 수 없어 업그레이드 요청에 토큰을 실을 방법이 없다.
`anyRequest().authenticated()` 아래 두면 **CONNECT 프레임까지 가지도 못하고 401 로 끝난다.**

구멍이 아니다. 인증은 CONNECT 에서 하고 구독 권한은 5.4 에서 따로 막으므로, 연 것은 업그레이드
자체뿐이다. **토큰을 쿼리 스트링에 넣는 우회는 쓰지 않는다** — 접속 로그에 그대로 남는다.

**연결 전에 `reissueOnce()` 를 한 번 거친다.** 토큰이 만료된 채로 연결하면 실패하는데, 소켓은
REST 처럼 401 을 받고 재발급하는 흐름이 없다.

한 번 맺은 연결은 토큰이 만료돼도 유지된다. 인증은 연결 시점에만 한다.

### 6.1 끊기면 방 목록으로 돌려보낸다

**재연결하지 않는다.**

서버가 연결 끊김을 곧 퇴장으로 처리하므로(4.2), 끊긴 순간 **그 사람의 좌석은 이미 사라졌다.**
소켓만 다시 열어도 그 방의 참가자가 아니다. 다시 들어가려면 `POST /join` 을 처음부터 다시
해야 하고, 그 사이 방이 꽉 찼거나 사라졌을 수 있으며 잠긴 방이면 비밀번호도 다시 받아야 한다.

가만히 두면 더 나쁘다. **화면이 거짓말을 한다** — 사람들이 그대로 서 있고 준비 버튼도 눌리는데
아무 일도 일어나지 않는다. 자기가 이미 방에서 나가졌다는 것을 알 방법이 없다.

그래서 끊기면 곧바로 방 목록으로 옮기고 이유를 알린다.

> 연결이 끊어져 방에서 나왔습니다.

되돌아온 이유가 분명하고, 다시 들어가려면 방을 누르면 된다. 자동 재입장을 흉내 내는 것보다
정직하다.

### 6.2 배포 경로 — **소켓만 Railway 에 직접 붙는다** (2026-08-23 실측)

`netlify.toml` 의 200 rewrite 는 **`Upgrade`·`Connection` 헤더를 떨군다.** 요청 자체는
Railway 까지 가지만 업그레이드가 성립하지 않아 Tomcat 이 400 으로 거절한다
(`Can "Upgrade" only to "WebSocket".`). 재시도로 풀릴 문제가 아니다.

브라우저에서 실제 오리진(`https://ibs-app.netlify.app`)으로 확인한 결과다.

| 경로 | 결과 |
|---|---|
| `wss://ibs-app.netlify.app/api/ws` | **실패** |
| `wss://<railway>/api/ws` | **101 Switching Protocols** |

**REST 는 그대로 프록시를 거친다.** refresh 쿠키가 서드파티 쿠키가 되면 Safari 가 막고
백엔드의 토큰 회전·재사용 탐지가 무력해진다. 이건 바뀌면 안 된다.

**그래서 소켓 인증에 쿠키를 쓸 수 없다.** 오리진이 갈리므로 서드파티 쿠키가 된다.
6장의 CONNECT 프레임 토큰 방식이 선택이 아니라 필수다.

같은 이유로 **백엔드 허용 오리진에 Netlify 주소가 들어가야 한다.** REST 는 프록시가 오리진을
지워 CORS 판정 자체가 없지만, 소켓은 브라우저가 진짜 오리진을 보낸다.

| | 소켓 주소 |
|---|---|
| 운영 | `VITE_WS_URL` 환경변수로 Railway 주소를 준다 |
| 개발 | 같은 오리진. `vite.config.ts` 의 proxy 에 `ws: true` 를 켠다 |

개발에서 프록시를 쓰는 이유는 dev 서버 포트가 `autoPort` 로 매번 달라져서, 백엔드 허용
오리진 목록에 고정할 수 없기 때문이다. HTTP 와 같은 이유다.

### 6.3 서버 인스턴스는 하나여야 한다

방이 인메모리라 이미 그랬는데, STOMP 심플 브로커도 인메모리라 **replica 를 늘리면 서로 다른
인스턴스에 붙은 사람끼리 메시지가 가지 않는다.** 지금은 replica 1개라 문제없지만, 늘릴 때는
방 저장소와 브로커를 함께 봐야 한다.

## 7. 화면

### 7.1 대기실

```
┌─────────────────────────────────────────────┐
│  점심내기 한판                   3/10   나가기 │
├─────────────────────────────────────────────┤
│                                             │
│      🧍   🧍   🧍   🧍   🧍      ← 뒷줄 5     │
│     이영희 박철수 강민지 최민수 정다은          │
│                                             │
│    🧍   🧍   🧍   🧍   🧍       ← 앞줄 5      │
│   김성호 오세훈 한지우 윤서준 서지훈           │
│    방장                                      │
├─────────────────────────────────────────────┤
│  내 아바타  [남] [여]              [준비]     │
└─────────────────────────────────────────────┘
```

- 인원이 5명 이하면 **앞줄만** 쓴다
- 준비한 사람은 연단에 표시가 붙는다
- 방장 연단에는 방장 표시
- 방장에게는 `[준비]` 대신 `[시작]`. **2명 미만이거나** 전원 준비 전이면 비활성

### 7.2 방장 양도

방장이 다른 사람의 연단을 누르면 확인창이 뜬다. `ConfirmDialog` 를 쓴다.

> **이영희 님에게 방장을 넘기시겠습니까?**
> 넘기면 되돌릴 수 없습니다.

양도한 뒤에는 `[시작]` 이 사라지고 `[준비]` 가 생긴다.

### 7.3 나가기

`나가기` 는 확인 없이 즉시 나간다. 되돌리기 쉬운 동작이라 확인창은 방해다.

`shared/ws` 가 `shared` 인 이유는 도메인 지식이 없기 때문이다 — "연결하고, 구독하고, 보낸다"가
전부다. 방·게임을 알면 `features` 로 내려가야 한다.

**방 상태를 Redux 에 넣지 않는다.** 소켓이 주는 것은 서버가 보낸 그대로의 최신 스냅샷이고,
RTK Query 캐시에도 넣지 않는다 — 무효화할 것이 없다. 방 화면이 `useState` 로 들고 있다가
언마운트되면 사라지는 것이 맞다.

`/topic/rooms`(목록)만 예외로, 받은 요약을 RTK Query 캐시에 써넣어 `useRoomsQuery` 와
같은 자리를 쓰게 한다. 화면 두 곳이 다른 진실을 갖지 않게 하려는 것이다.

## 9. 폐기한 대안

**한 줄 배치.** 10명이면 아바타가 34px 이다. 첨부된 클레이 아바타는 얼굴이 살아야 하는
디자인이라 그 크기에서 뭉개지고, 이름도 세 글자를 넘으면 잘린다.

**차례인 사람이 중앙으로 나오는 연출.** 보기에는 제일 좋지만 3초 제한 시간에 매번 이동
애니메이션이 끼면 정신없고, 이동 중에 답이 들어오면 말풍선을 어디에 띄울지 애매하다.

**전원 준비 시 자동 시작.** 마지막 사람이 준비를 누르는 순간 판이 시작되어, 손이 버튼 위에
있는 채로 첫 턴을 맞는다.

**아바타를 계정에 저장.** `users` 에 컬럼이 늘고 백엔드 일이 늘어난다. 지금 고를 수 있는
것이 둘뿐이라 방마다 다시 고르는 비용이 낮다. 종류가 늘어나면 그때 다시 본다.

**채팅.** 답을 말풍선으로 띄우는 것이 이미 대화처럼 보인다. 입력칸이 둘이 되면 답을 어디에
치는지 헷갈리고, 게임 중에 채팅으로 답을 알려주는 일도 생긴다.

**방 상태를 조각내어 브로드캐스트.** 참가자 목록·준비·방장을 따로 보내면 순서가 뒤집혔을 때
화면이 어긋나고, 재접속한 사람에게 현재 상태를 다시 만들어 줄 방법이 없다. 10명짜리 방의
상태는 작다.
