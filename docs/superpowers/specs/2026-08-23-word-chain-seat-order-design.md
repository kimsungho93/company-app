# 끝말잇기 좌석 순서 — 화면이 곧 턴

선행 문서: [전체 그림](2026-08-22-word-chain-design.md) · [대기실](2026-08-23-word-chain-room-design.md) · [게임 진행](2026-08-23-word-chain-game-design.md)

## 1. 무엇을 바꾸나

턴 순서가 화면과 무관하게 시작 시점 셔플로 정해진다. 누가 다음인지 화면만 봐서는 모른다.

- 셔플을 없애고 **`players` 배열 순서 = 좌석 순서 = 턴 순서** 로 만든다
- 방장이 대기실에서 **드래그로** 순서를 바꾼다. 키보드로도 된다

범위 밖 — 게임 중 재배치 · 무작위 섞기 버튼 · 순서가 바뀔 때 좌석 이동 애니메이션.

## 2. 결정 요약

| 결정 | 왜 |
|---|---|
| 순서의 진실은 서버 `players` 배열 하나 | 클라에서 정렬하면 사람마다 "왼쪽"이 다른 사람이다 |
| 셔플 삭제. 다음 판도 그대로 | 섞고 싶으면 방장이 손으로 섞는다 |
| `/order` 는 전체 배열 | 스왑은 하나만 유실돼도 영원히 어긋난다. `ready` 가 토글이 아닌 것과 같은 원리 |
| 경합은 관대한 합치기 | 드래그 중 입장·퇴장과 부딪힌다. 엄격 거절은 방장에게 영문 모를 오류다 |
| 핸들 드래그 · pointer events · 라이브러리 없음 | HTML5 DnD 는 터치에서 안 움직인다. dnd-kit 은 리스트 하나에 의존성이다 |
| 놓은 순서는 다음 브로드캐스트까지 로컬 유지 | 스냅백 깜빡임을 막는다. 서버 주도 원칙의 명시된 예외 |

## 3. 순서 규칙

배열 인덱스 순서가 전부다.

```
5명 이하   한 줄. 왼 → 오
6명 이상   뒷줄 왼 → 오, 그다음 앞줄 왼 → 오
```

`splitSeats` 가 배열 앞 절반을 뒷줄에 놓으므로 **규칙이 곧 렌더 순서다.** 프론트에 순서 계산이
하나도 안 생긴다.

첫 차례는 배열 첫 사람 — 화면 맨 왼쪽(뒷줄이 있으면 뒷줄 왼쪽 끝)이다. 탈락자는 차례만
건너뛰고 자리는 그대로다(기존 규칙). 기본 순서는 지금처럼 입장 순이고, 셔플이 사라질 뿐이다.

## 4. 소켓 계약

```
보냄   /app/rooms/{id}/order      { "userIds": [9, 2, 5] }
받음   없음 — 방 스냅샷 브로드캐스트가 응답이다
```

- **방장만, `WAITING` 일 때만.** 아니면 기존 오류 채널로 거절
- **전체 배열을 보낸다.** 멱등이라 재전송·유실에 안전하다
- **서버는 관대하게 합친다** — 방에 없는 id 는 버리고, 메시지에 빠진 참가자는 기존 상대
  순서를 지켜 뒤에 붙인다
- `Game` 은 시작할 때 순서 복사본을 들므로, 판 도중 순서가 바뀌어도 진행 중인 판은 안 흔들린다

## 5. 드래그

방장에게만, 대기실에서만 연단에 핸들이 보인다.

- **핸들이 따로 있는 이유** — 연단에는 방장 넘기기 클릭이 이미 있다. 연단 전체를 드래그로
  만들면 클릭과 드래그가 싸운다
- pointerdown → `setPointerCapture` → 다른 연단 중심을 지나면 미리보기 순서 교체 →
  pointerup 에 `/order` 전송. 놓기 전에는 아무것도 안 보낸다
- 핸들에 `touch-action: none` — 없으면 터치 드래그가 스크롤로 새어 나간다
- **키보드** — 핸들이 `<button>` 이다. 포커스 후 좌우 화살표로 한 칸씩. 누를 때마다 전체
  배열을 보낸다(멱등이라 문제없다). 드래그만 있으면 키보드 사용자는 순서를 못 바꾼다

## 6. 놓은 뒤 — 로컬이 잠깐 이긴다

방 상태는 서버 주도라, 놓는 순간과 브로드캐스트 사이(~100ms)에 원래 순서로 **스냅백했다가
다시 움직인다.** 드래그에서 이건 렉이 아니라 고장으로 보인다.

놓은 순서를 로컬에 들고 있다가 **다음 방 스냅샷이 오면 무조건 버린다.** 서버가 거절했든 다른
이유로 순서가 다르든 스냅샷이 진실을 복원한다. "받은 스냅샷을 그대로 그린다" 원칙의 예외는
이 한 곳이고, 수명은 브로드캐스트 한 번이다.

## 7. 프론트 구조

- `Stage` 가 `onReorder?: (userIds: number[]) => void` 를 받는다. **콜백이 있으면 핸들을
  그린다** — 방장·대기실 판단은 `RoomView` 가 해서 콜백을 줄지 말지로 표현한다
- `RoomView` 는 계속 소켓을 모른다. `RoomActions` 에 `order(userIds)` 가 는다
- 드래그 상태(잡은 id · 미리보기 순서)는 `Stage` 내부 로컬 state 다. Redux 에 안 간다

## 8. 검증

| 확인할 것 | 판별점 |
|---|---|
| 화면 = 턴 | 시작하면 뒷줄 왼쪽 끝부터 차례가 온다 |
| 드래그 | 방장이 끌어 놓으면 모든 참가자 화면이 같은 순서로 바뀐다 |
| 스냅백 없음 | 놓는 순간 순서가 튀지 않는다 |
| 비방장 | 핸들이 안 보인다. 강제로 보내면 거절된다 |
| 게임 중 | 핸들이 사라진다 |
| 키보드 | 핸들 포커스 + 화살표로 이동한다 |
| 경합 | 드래그 중 입장한 사람이 목록 끝에 붙는다 |

## 9. 폐기한 대안

| 대안 | 왜 안 하나 |
|---|---|
| 셔플 유지 + 시작 때 좌석 재배치 | 시작 순간 전원이 자리를 바꿔 튄다. "좌석은 판이 끝날 때까지 안 움직인다"와 정면 충돌 |
| 클라이언트에서 정렬 | 사람마다 왼쪽이 다른 사람이 된다 |
| 스왑 메시지 (a↔b) | 하나 유실되면 화면과 서버가 영원히 어긋난다 |
| dnd-kit | 리스트 하나에 의존성. 터치·키보드는 직접 구현으로 충분하다 |
| 연단 전체 드래그 | 방장 넘기기 클릭과 싸운다 |
| 집합 불일치 시 엄격 거절 | 드래그 중 입장·퇴장은 자연스러운 일이다. 방장이 영문 모를 오류를 본다 |
