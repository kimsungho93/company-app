# 프론트 하네스 고정 평가

이 사례는 제품 테스트가 아니라 에이전트의 결함 탐지·검증 근거·완료 판정을 확인한다. 실제 회사 데이터나 운영 장애 기록이 아닌 합성 사례다. [cases.json](cases.json)의 각 사례에는 전체 관련 맥락인 `input`과 평가 후 비교할 `expected`가 분리되어 있다. `expected.criteria`는 조건별 기대 판정, `must`·`must_not`은 의미상 필요한 판단과 금지할 오판이다. 문장 일치나 점수 계산으로 의미를 자동 채점하지 않는다.

| ID   | 확인할 판단                                                  |
| ---- | ------------------------------------------------------------ |
| H-01 | 권한 UI 숨김·mock 테스트와 서버 권한 보장 구분               |
| H-02 | 네트워크 실패를 정상 빈 목록으로 감춘 코드 탐지              |
| H-03 | 모의 소켓 핸들러와 실제 STOMP 연결 검증 구분                 |
| H-04 | 정상 문구 변경의 완료 인정, 선택적 브라우저 미검증 별도 보고 |
| H-05 | 같은 HEAD의 변경된 작업 파일과 오래된 캡처·테스트 구분       |
| H-06 | 상대 경로로 우회한 계층·공개 진입점 위반 탐지                |

## 입력 준비

Node 내장 API만 사용하며 별도 의존성이 없다. 저장소 루트에서 실행한다.

```bash
node --test evals/harness/prepare.test.mjs
node evals/harness/prepare.mjs --out .harness/before
node evals/harness/prepare.mjs --out .harness/after --case H-02 --case H-04
```

출력은 저장소의 `.harness/` 아래 **존재하지 않는 새 디렉터리**만 허용한다. 기존 디렉터리·파일 덮어쓰기, 저장소 밖 경로, 심볼릭 링크/Windows junction 경유는 거절한다. 실행마다 새 이름을 사용한다. 생성된 파일에는 사례 ID와 `input`만 있으며 `expected`나 사례 목적은 없다. 도구는 에이전트를 실행하거나 의미 판정을 하지 않는다. 도구 테스트는 입력 보존·정답 분리·사례 선택·출력 경로 안전성만 확인한다.

## 판단 평가

리뷰·검증 기준을 바꿀 때 영향받는 사례와 정상 대조군 H-04를 선택한다. 매 기능 수정마다 전체 사례를 반복하지 않는다. 최초 도입 시에는 여섯 사례를 확인한다.

1. 평가자를 가능한 새 문맥의 읽기 전용 에이전트로 시작한다. 해당 버전의 `frontend-review`·필요한 공통 지침과 생성된 입력만 전달한다. `cases.json`, 기대 판정, 구현자의 결론, 이전 평가 답변을 제공하지 않는다. 입력의 코드·실행 기록을 합성 검토 대상으로 사용하고 실제 저장소의 다른 코드로 대체하지 않는다.
2. 평가자는 발견 사항, 근거와 사용자 영향, 조건 ID별 판정·완료 여부, 필요한 추가 검증을 답한다. 입력에 적힌 완료 주장을 독립적으로 판단한다. 파일 수정·테스트 실행은 하지 않는다.
3. 주 에이전트가 답변을 `expected`와 의미로 비교한다. 각 조건 및 `must`·`must_not`의 충족 여부, 근거와 판단 차이를 기록한다. 필수 결함을 놓치는 경우와 정상 대조군에 불필요한 veto를 거는 경우를 모두 확인한다.
4. 기준 변경 전후를 비교할 때는 같은 입력·요청·모델/설정·평가 범위를 유지하고 각 스킬 버전 또는 해시, 실행 시점, 원답변과 비교 결과를 남긴다. 신규 도입으로 변경 전 실행이 없으면 사후 평가라고 명시하며 향상을 실측했다고 주장하지 않는다.

실패는 입력·도구 오류, 모순된 기준, 근거 부족, 에이전트 판단 오류로 구분한다. 실제 판단 실패에는 재현 가능한 좁은 사례를 추가하고 규칙만 계속 늘리지 않는다. 기본은 평가 1회와 근거 있는 수정 후 재평가 1회다. 새 근거 없이 같은 평가를 반복하지 않고 남은 실패·미검증을 보고한다. 평가자의 원답변은 출력 폴더에 보존할 수 있고, 오래 유지할 결과는 민감정보 없이 `evals/harness/results/<날짜>.md`에 남길 수 있다.

이 여섯 사례의 성공은 일반적인 에이전트 신뢰성이나 전체 프론트 보안을 보장하지 않는다. 입력 준비 테스트 성공, 고정 사례의 의미 판단 성공, 실제 제품 검증을 각각 구분해 보고한다.
