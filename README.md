# company-app

사내 인증·승인 관리·휴가·끝말잇기·사람 뽑기를 제공하는 React 프론트엔드다. 백엔드 `company-backend`와 REST·STOMP 계약을 공유한다. 가입 후 관리자의 승인이 필요하며 다크·라이트 테마를 지원한다. 로그인·회원가입 화면은 다크 테마를 사용한다.

## 실행

Node.js 24와 저장소에 포함된 Yarn 4를 사용한다. 실제 버전은 `package.json`·`yarn.lock`과 CI 설정을 기준으로 한다.

```bash
yarn install --immutable
yarn dev
```

Yarn 명령을 사용할 수 없는 환경에서는 `node .yarn/releases/yarn-4.18.0.cjs <명령>`으로 실행한다. `.yarnrc.yml`과 Yarn 릴리스 파일을 유지하며 패키지 매니저를 혼용하지 않는다. 의존성 변경 시 Yarn으로 lockfile을 갱신한다.

실제 백엔드 연동에는 `../../backend/company-backend`에서 개발 DB와 서버를 실행한다. 백엔드의 현재 지침을 먼저 확인한다. PowerShell에서는 `docker compose up -d --wait` 후 `.\gradlew.bat :bootstrap:bootRun`, macOS/Linux에서는 `bash gradlew :bootstrap:bootRun`을 사용한다. 기본 프록시는 `/api`를 `localhost:8080`으로 전달한다. 개발 프론트 포트는 5173이며 `PORT` 환경변수로 바꿀 수 있다.

| 명령                                         | 범위                                                                    |
| -------------------------------------------- | ----------------------------------------------------------------------- |
| `yarn dev`                                   | Vite 개발 서버                                                          |
| `yarn format` / `yarn format:check`          | Oxfmt 적용 / 검사                                                       |
| `yarn lint`                                  | 기존 Oxlint 규칙 검사                                                   |
| `yarn check:architecture`                    | 별칭·상대 경로를 해석한 모듈 경계 검사                                  |
| `yarn test:architecture`                     | 모듈 경계 검사기의 고정 회귀 테스트                                     |
| `yarn test`                                  | Vitest 단위·컴포넌트 테스트                                             |
| `yarn vitest run <파일>`                     | 관련 Vitest 테스트                                                      |
| `yarn build`                                 | TypeScript 검사 후 Vite 프로덕션 빌드                                   |
| `yarn test:e2e`                              | 빌드 후 Playwright 핵심 브라우저 smoke                                  |
| `yarn test:harness`                          | 하네스 평가 입력 준비 도구의 회귀 테스트                                |
| `yarn verify`                                | 포맷·린트·모듈 경계와 검사기 테스트·하네스 도구 테스트·단위 테스트·빌드 |
| `yarn verify:all`                            | 기본 검증과 Playwright smoke                                            |
| `yarn preview`                               | 빌드 결과 확인용 서버                                                   |
| `node --test evals/harness/prepare.test.mjs` | 하네스 평가 입력 준비 도구의 안전성·출력 테스트                         |

브라우저 smoke를 처음 실행할 때는 `yarn playwright install chromium`으로 브라우저를 준비한다. Linux CI에서 시스템 라이브러리도 필요하면 `yarn playwright install --with-deps chromium`을 사용한다. Playwright는 프로덕션 빌드를 `127.0.0.1:5187`의 Vite preview로 실행하며 기존 서버를 재사용하지 않는다. `test:e2e`는 먼저 빌드하고 `verify:all`은 기본 검증에서 만든 빌드를 사용한다. 실패 보고서는 `playwright-report/`, 실행별 부속 자료는 `test-results/`에서 확인하며 이전 실행의 결과를 새 실행으로 보고하지 않는다.

Playwright smoke는 **실제 Chromium에서 mock REST 응답으로 화면 흐름을 검증**한다. 서버 권한·refresh 쿠키 발급/회전·실제 STOMP 연결을 입증하지 않는다. 실제 서버 연결이 완료 조건이면 별도로 실행하고 서버·프론트 버전, 계정 역할, 요청/응답이나 연결 관찰을 민감정보 없이 기록한다.

## 구조와 화면

React·TypeScript·Vite·Redux Toolkit/RTK Query·React Router·SCSS Modules를 사용한다. 검증 도구는 Oxlint·Oxfmt·Vitest·Playwright다. Oxfmt는 2칸 들여쓰기, 작은따옴표, 세미콜론 생략, 폭 100, LF로 설정한다.

```text
src/app → pages → widgets → features → shared
```

`app`은 라우팅·store·설정, `pages`와 `widgets`는 화면 조립, `features`는 업무 기능, `shared`는 도메인 독립 요소를 맡는다. 하위 계층을 바로 참조할 수 있지만 상위 참조는 금지한다. feature 외부에서는 공개 `index.ts`만 사용하고 서로 다른 feature의 연결은 상위 계층에서 조립한다. 별칭만 검사하는 린트로 상대 경로까지 보장했다고 판단하지 않는다.

| 경로                                             | 화면                |
| ------------------------------------------------ | ------------------- |
| `/login`, `/signup`                              | 로그인·회원가입     |
| `/`                                              | 홈                  |
| `/admin/users`                                   | 승인 관리           |
| `/leave`                                         | 휴가                |
| `/games/word-chain`, `/games/word-chain/:roomId` | 끝말잇기 방 목록·방 |
| `/games/lottery`, `/games/lottery/:roomId`       | 사람 뽑기 로비·방   |

인증 가드는 레이아웃 바깥에 두며 `AuthBootstrap`이 복구를 마치기 전이나 일시 장애 상태에서는 보호 라우터를 표시하지 않는다. 관리 화면과 메뉴의 역할 검사는 사용자에게 보여 줄 UI를 정한다. 서버의 요청별 권한 검사는 별도로 필요하다. 인증 배경의 웨이퍼 애니메이션은 회사의 반도체·스마트팩토리 맥락을 반영한다.

개발 시 다음 설정을 함께 확인한다.

- `@/` 별칭은 `vite.config.ts`와 `tsconfig.app.json` 양쪽에서 유지한다. 새 루트 TypeScript 도구 설정은 해당 tsconfig의 `include`에 들어가는지 확인한다.
- TypeScript는 사용하지 않는 선언과 잘못된 타입 import를 빌드에서 검사한다. 런타임 `enum`이나 생성자 파라미터 프로퍼티는 기존 설정과 맞지 않는다. 증분 캐시가 의심되면 `yarn tsc -b --force`로 확인한다.
- Yarn의 peer dependency 경고는 해당 패키지 사용처와 실행 결과로 확인한다. 설치 성공만으로 런타임 의존성 충족을 단정하지 않는다.
- 함수 표현식은 기존 Oxlint 규칙을 따른다. SCSS는 `@use`/`@forward`와 역할별 디자인 토큰을 재사용한다. `<html data-theme>` 및 첫 페인트 전 테마 적용을 유지한다.
- REST 프록시는 refresh 쿠키와 관계되며 개발의 `vite.config.ts`, 운영의 `netlify.toml`을 함께 확인한다. 운영 WebSocket은 `VITE_WS_URL`과 `shared/ws/wsUrl.ts`를 확인한다. 실제 배포 환경의 설정 여부는 저장소만 보고 단정하지 않는다.

## 계획과 완료 평가

여러 단계 기능·중요한 리팩터링 또는 명시적 계획 요청에는 구현 전에 `PLAN.md`를 작성한다. 작은 수정은 같은 핵심 정보를 작업 설명에 남기면 충분하다. 계획에는 목표·범위·사용자 결정, 기준 커밋과 기존 미커밋 변경, 조건 ID, 실행 순서, 검증 방법, 결정 변경과 남은 작업을 담는다. 파일을 만들었다는 사실보다 사용자가 관찰할 행동과 실패 결과를 조건으로 적는다.

| ID   | 구분 | 관찰할 결과                                        | 검증 방법                        | 상태   | 근거   |
| ---- | ---- | -------------------------------------------------- | -------------------------------- | ------ | ------ |
| AC-1 | 필수 | 조회 실패 시 오류와 재시도를 표시한다.             | 실패 응답을 주는 컴포넌트 테스트 | 미검증 | 미실행 |
| AC-2 | 필수 | 대화상자를 닫으면 실행 버튼으로 포커스가 돌아온다. | 실제 브라우저 키보드 흐름        | 미검증 | 미실행 |
| AC-3 | 권고 | 추가 브라우저에서도 같은 화면을 확인한다.          | 별도 브라우저 관찰               | 미검증 | 미실행 |

판정은 `통과`, `실패`, `미검증`, `해당 없음`이다. 필수 조건의 실패·미검증이 남으면 완료가 아니다. 권고 조건은 별도로 보고하고 필수 통과를 취소하지 않는다. 해당 없음에는 적용되지 않는 이유를 남긴다. 조건별 표가 채점의 기준이며 필요하면 필수/권고의 통과 수를 각각 집계한다. 통과 수나 평균 점수로 필수 실패를 상쇄하거나 전체 품질을 보장하지 않는다. 계획에서 누락된 원래 요구와 기존 계약도 확인한다.

근거에는 명령·결과·시점·보고서 경로 또는 관찰 내용과 검증한 코드 상태를 연결한다. HEAD만으로 미커밋 코드를 식별할 수 없으므로 실제 diff·새 파일과 필요 시 관련 파일 해시를 남긴다. 이후 변경이 검증 대상에 영향을 주면 해당 근거를 재확인한다. 오래된 캡처·테스트, 실행하지 못한 조건, 정적 확인만 있는 실행 조건은 미검증이다.

새 요구나 확인된 사실로 조건을 바꿀 때는 이전 조건·변경 이유·영향을 기록한다. 통과시키기 위한 조건 삭제나 검사의 약화는 하지 않는다. 마일스톤·검증·리뷰·인수인계에서 같은 ID를 갱신하고 반복 채점 자체를 목표로 삼지 않는다. 무관한 진행 중 PLAN을 덮어쓰지 않으며 동시 작업은 별도 체크아웃이나 지정한 `docs/plans/<작업명>.md`를 사용한다. 새 계획으로 교체할 때 보존할 이전 결과를 이력 또는 별도 작업 문서에 남긴다.

## 검증 선택

변경에 직접 영향을 받는 검증부터 실행한다. 충분한 근거가 있으면 새 변경이나 실패 없이 같은 검사를 반복하지 않는다.

| 변경·완료 조건                            | 필요한 검증과 한계                                                                                                    |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 문서·문구·포맷                            | diff·참조·명령 정합성과 포맷 검사. 동작 변경이 없으면 별도 브라우저 확인은 위험과 요구에 따라 선택한다.               |
| 순수 함수·업무 계산                       | 정상·거절·경계의 관련 Vitest 회귀 테스트, lint·build                                                                  |
| 컴포넌트·상태·요청 처리                   | 관련 컴포넌트 테스트와 로딩·오류·빈 상태, lint·build. 취소·늦은 응답·언마운트 정리 등 영향받은 흐름 확인              |
| UI 동작·공통 대화상자·접근성              | 관련 테스트와 실제 브라우저의 키보드·포커스·테마·반응형. 기존 smoke가 변경을 다루는지 확인하고 필요한 흐름 보완       |
| 인증·세션·권한·REST/STOMP 계약            | 관련 단위·컴포넌트 및 브라우저 흐름. 서버 보장·실제 쿠키/소켓 연결이 조건이면 실제 백엔드 증거 추가, 계약·사용처 확인 |
| import·폴더·별칭·경계 검사기              | `check:architecture`와 `test:architecture`, lint·build. 상대 경로와 공개 진입점 우회 확인                             |
| 의존성·도구·테스트/CI 설정·여러 기능 변경 | `verify:all` 및 변경한 도구의 회귀 테스트. 검사 제외·실행 범위가 기존 보장을 줄이지 않는지 확인                       |
| 리뷰·검증 판단 기준                       | 영향받는 고정 평가 사례와 정상 대조군. 입력 생성 테스트만으로 의미 판단을 검증했다고 보고하지 않음                    |

`verify`는 일반적인 공통 기준이다. `verify:all` 성공도 모든 화면·브라우저·실제 서버 연동을 보장하지 않는다. 해당 실행 환경이 없으면 가능한 검사를 마치고 충족하지 못한 조건과 이유를 보고한다. 환경 실패와 제품 결함을 구분하되 둘 다 근거 없이 통과로 처리하지 않는다. mock이 성공한 단위 테스트를 실제 브라우저 관찰로, mock REST 브라우저 테스트를 실제 서버 통합 검증으로 바꾸어 보고하지 않는다.

성능에 영향을 줄 때는 반복 API 호출, 불필요한 재렌더링, 구독·타이머·소켓 정리, 큰 목록과 번들 비용을 확인한다. 측정이 필요한 조건이면 같은 데이터·상호작용·환경으로 전후를 비교하고 실제 측정·편차·추정을 구분한다. 모든 수정에 벤치마크를 요구하지 않는다.

## 독립 리뷰와 인수인계

업무 로직·인증·세션·REST/STOMP 계약·공통 UI 동작·의미 있는 리팩터링은 관련 검증 후 별도 서브에이전트가 `frontend-review`로 읽기 전용 검토한다. 가능한 새 문맥에 원래 요구, 계획 경로, 기준 커밋과 실제 diff·새 파일, 관련 계약, 명령·관찰 근거를 전달한다. 구현자의 합격 결론을 정답으로 주지 않는다. 구현 대화를 상속했다면 문맥이 완전히 분리되었다고 보고하지 않는다.

리뷰어는 파일·계획을 수정하거나 테스트·포맷·설치 명령을 실행하지 않는다. 필요한 추가 검증은 대상과 이유로 반환한다. 주 에이전트가 의견의 근거를 확인해 수용·기각·보류와 이유를 남기고 수정·검증·계획 갱신을 맡는다. 기본은 최초 리뷰 1회와 수정 후 재리뷰 1회다. 재리뷰는 수정과 영향 범위·새 근거에 집중하며 같은 주장이나 새 근거 없는 반복을 끝낸다. 남은 문제를 해결된 것으로 바꾸지 않고 미해결·미검증을 보고한다. 별도 에이전트가 불가능하면 같은 기준으로 자체 검토하고 독립성의 한계를 밝힌다.

리뷰는 재현 가능한 결함·계약 위반·필수 검증 누락을 우선하며 취향성 변경을 자동으로 구현하지 않는다. 인증·권한·외부 입력·비밀정보 변경은 스킬의 보안 기준을 같은 리뷰 안에서 적용한다. 발견 사항 없음은 서비스 전체의 보안 인증이 아니다.

위임·중단 시 다음 정보를 메시지나 PLAN의 인수인계 부분에 남긴다. 일반 완료 보고로 충분하면 별도 문서를 만들지 않는다.

- 목표·사용자 결정·허용된 범위, 저장소/체크아웃·브랜치·HEAD, 기존 변경과 이번 변경·새 파일
- 실제 계획 경로와 미충족 조건 ID, 중요한 결정·계약, 실행 명령·시점·결과·검증 코드 상태·근거 경로
- 남은 작업과 다음 행동, 실행 중인 명령·다른 담당자, 미검증 이유

인수자는 현재 요청·지침과 실제 파일 상태를 대조하고 재사용 가능한 근거를 확인한 뒤 이어간다. 같은 HEAD여도 관련 작업 파일이 바뀌었으면 이전 통과를 그대로 가져오지 않는다. 인수 기록이 권한을 확대하지 않으며 토큰·비밀번호·개인정보·원본 민감 로그를 복사하지 않는다.

## 기술 결정과 문서

새 주요 의존성·상태 저장·외부 서비스·배포 방식은 문제와 필수 조건을 먼저 적고 기존 방식 유지를 포함한 실질적인 대안을 비교한다. 현재 환경 호환성, 필요한 동작 보장, 개발·운영·교체 비용과 감수할 단점으로 선택한다. 공식 문서의 버전·지원 범위, 실행 근거, 가정을 구분하고 결정을 좌우하는 불확실성이 있을 때만 성공 기준을 정해 작은 실험을 한다. 오래 유지할 결정은 `docs/adr/`에 배경·대안·선택과 단점·근거·재검토 조건을 간단히 남긴다.

API 계약은 [docs/api](docs/api), 화면별 설계는 [docs/superpowers/specs](docs/superpowers/specs)에 있다. 변경한 기능의 문서만 선택해 읽고 REST 필드·오류 코드·권한·날짜·STOMP 이벤트 변경은 실제 백엔드 사용처와 함께 확인한다. 완료 보고에는 변경 범위, 실행한 검증과 결과, 리뷰 의견 처리, 남은 필수·권고 조건과 미검증 이유를 담는다.
